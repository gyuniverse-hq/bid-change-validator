## 결론

남은 문제는 표현 지침 부족 하나로 설명되지 않는다. (1) 서류와 제출 단계의 관계를 모델의 자유 기입에 맡김, (2) 현재 질문의 완료 기준과 최초 job의 완료 기준을 혼용함, (3) 원문 재사용과 검증된 업무 항목 재사용이 분리되지 않음, (4) 긴 답변의 보완을 다음 질문으로 미루는 정책이 함께 작용한다. 문장별 검증은 일부 잘못된 설명을 거절하지만 업무 전체의 미해결 사항을 끝까지 보존하지 못한다.

## 1. 서류·기한 혼합

`submission_obligations.py:10`의 document/stage/deadline은 각각 문자열이다. 한 문자열에 여러 서류·시점을 넣는 것을 막지 않는다. 같은 단계·기한·방법인 경우만 묶으라는 제한은 프롬프트이며, 서류 ID별 의무나 필드별 근거 관계가 아니다.

`answer_validation.py:249`는 생성 시 선택적 submission을 받고 `:263`에서 텍스트로 바꿔 기존 문장 검증으로 보낸다. 원문에서 확정한 서류별 의무 원장이 생성에 앞서 존재하지 않는다. 검증 완료 후에도 submission 구조는 Claim에 보존되지 않는다.

실제 마지막 응답의 C18 거절 사유는 안전보건관리계획서(낙찰예정자 선정 후)와 안전보건관리 이행서약서(계약체결 시)의 기한을 합쳤다는 것이다. source `s-2d0a5c825d8effdee5de`에 두 시점이 명시되어 있으므로 이 사례를 단순 원문 미확보로 설명할 수 없다. 최종 보고서에는 거절된 초안 전문이 없으므로 정확한 초안 문구는 UNVERIFIED이며, 위 설명은 검증 사유와 원문 대조에 근거한다.

## 2. 준비 순서 오류

준비 순서를 문단으로 만들라는 지침은 있지만, ‘자료 준비 → 제출 → 해당 자료로 발표’의 선후 관계와 제출기한을 코드가 비교하는 구조는 없다. 제출 항목 구조도 준비 행동의 의존 관계를 담지 않는다.

첫 응답 c19는 제안서/USB 자료를 제출 이후 마지막에 준비하는 순서 때문에 거절됐다. 발표 단계에서 사용할 자료와 입찰 단계에서 미리 제출할 자료를 연결하지 못한 것이다. 특정 문구의 수정만으로 다른 서류의 같은 유형 오류까지 예방했다고 볼 수 없다.

## 3. 더 중요한 문제: 원래 job의 미완료 기준이 사라짐

실제 기록:

| 턴 | 남은 검사 기준 | 처리 상태 | job 상태 |
| --- | --- | --- | --- |
| 참여 준비 전체 | READ_CHECKS:7, GOAL:request | PARTIAL | OPEN |
| 처음 요청의 남은 일 | READ_CHECKS만 평가, 미충족 기준 없음 | PASS | COMPLETE |
| 실행 체크리스트 | 기준은 모두 MET이지만 C18 모순 거절 | PARTIAL | OPEN, remaining=[] |

두 번째 응답에서 최초 GOAL:request를 다시 검사하지 않았는데 job COMPLETE가 됐다. 따라서 앞선 보고의 ‘두 번째 응답만 PASS’라는 설명 외에, **제품 화면의 job COMPLETE가 과도한 완료 표시였다는 문제**를 추가해야 한다.

코드 경로:

1. `orchestration.py:202`는 plan.goal을 현재 사용자 메시지로 설정한다. 현재 요청을 존중하는 동작 자체는 필요하다.
2. `acceptance.py:161`는 현재 도구 종류가 둘 이상일 때만 GOAL:request를 만든다. 두 번째 턴은 READ_CHECKS 하나여서 처음의 전체 업무 기준이 없다.
3. `job_state.py:135`의 requirement 상태는 도구별 기준으로 저장된다. GOAL 기준은 독립 requirement로 보존되지 않는다.
4. `job_state.py:155`는 job.remaining을 현재 턴의 기준으로 교체하고, `:157`은 현재 턴 complete와 도구 requirement 완료를 조합한다. 최초 GOAL 미완료가 사라질 수 있다.
5. 세 번째 턴은 문장 모순으로 PARTIAL이지만 criteria 결과는 모두 MET이었다. 문장 실패 사유와 남은 업무 기준의 연결이 없어 OPEN인데 remaining은 빈 배열이다.

이는 검증을 느슨하게 해서 해결할 문제가 아니다. 최초 job의 의무/완료 기준, 현재 요청 산출물, 문장 검증 상태를 구별하고 연결해야 한다.

## 4. 반복과 이어가기의 제한

READ_CHECKS와 READ_DOCUMENT가 같은 공동수급 제한·접수 의무를 서로 다른 근거로 가져온다. 최종 응답에서 공동수급 금지와 방문 접수 안내가 반복됐다.

`answer_validation.py:456`의 중복 제거는 공백 정리한 동일 문장 + 같은 fact/source ID + 같은 화행에 한정된다. 의미가 같아도 표현이나 근거가 다르면 남는다. 확인 대상 혼합 방지(MIXED_CHECK_ENTITIES)는 필요한 안전장치지만, 여러 확인 항목을 한 문장으로 요약하는 모델 출력을 거절하므로 별도의 사용자 표시 묶음과 함께 설계해야 한다.

`answer_progress.py:12`의 재사용 키에는 현재 goal, 기준, 전체 근거가 포함된다. `:23`은 동일 키와 resume flag가 모두 맞아야 검증된 설명을 재사용한다. 표현이 바뀐 후속 요청에서는 그대로 재사용되기 어렵다. 이번 두 번째 질문은 resume=true여도 첫 질문과 goal/도구가 달랐다. 세 번째 질문은 resume=false였다.

`document_memory.py`는 같은 fingerprint의 원문 조각을 보존한다. 검증된 ‘서류별 의무/사용자가 이미 받은 설명’의 원장을 유지하는 기능은 아니다. 현재 안전한 재사용 조건을 단순 완화하면 오래된 판정·다른 질문을 잘못 재사용할 수 있으므로 권장하지 않는다.

## 6. 왜 504 PASS로 잡히지 않았나

추가 submission 테스트는 가짜 모델이 이미 분리한 두 행을 제공한다. 필드가 검증기로 전달되는지, CONTRADICTED가 유지되는지 확인한다. 실제 모델의 올바른 서류 분리·준비 순서·전체 job 완결성을 입증하지 않는다. 기존 단위 회귀 통과와 실제 업무 흐름 통과를 구분해야 한다. 이번 실제 세 턴에서 위 문제를 확인했으므로 테스트를 더 만들어 숫자를 올리는 것이 우선순위는 아니다.

## Q-017 — 설계 대화에 전달할 판단 요청

**문제:** 현재 구현은 job 기록을 갖지만 핵심 완료 판단은 현재 턴의 도구/문장 중심이다. 원래 업무의 실패 기준이 후속 질문에서 소실될 수 있다. 제출 구조도 검증 전 임시 답변 형식에 머문다.

**근거:** 최초 GOAL:request MISSING → 후속 READ_CHECKS만 검증 → job COMPLETE; 세 번째 모순 거절인데 remaining=[]; 실제 서류 단계 병합 거절. 코드와 실행 근거는 위 항목 참조.

**대안 A:** 프롬프트·출력 길이·접힘 UI만 추가 보완. 비용은 작지만 완료 기준 소실과 관계 혼합을 구조적으로 막지 못한다.

**대안 B — 권장:** 현재 구조를 유지하되 job에 완료 의무와 미해결 사유를 별도 보존한다. 서류별 제출 의무(서류/단계/주체/기한/방법/조건/근거)를 검증해 재사용하고, 사용자 요청별로 요약/순서/체크리스트를 만든다. 관계가 불명확하면 해당 항목을 보류한다. 원문·프로필 변경 시 관련 항목만 무효화한다. 먼저 완료 기준 소실과 빈 remaining을 막고, 다음으로 의무 분리와 준비 순서, 마지막으로 재사용·출력 길이·속도를 평가한다.

**대안 C:** 전면 재설계. 범위·회귀 위험이 커 현재 증거만으로 즉시 권장하지 않는다.

**수용 기준:** 표현이 다른 이어가기에도 최초 미완료가 남아 있을 것; 부분 실패가 있으면 남은 이유가 표시될 것; 서로 다른 제출 시점을 합치지 않을 것; 준비 순서가 제출기한과 충돌하지 않을 것; 의미상 반복·시간은 동일 세 턴을 기준으로 별도 측정할 것. 한 사례 성공을 Core 전체 성공으로 일반화하지 않는다.

이번 산출물은 분석 보고서뿐이다. 코드 수정, 새 모델 비용, merge·배포는 없다.
