# 과업 중심 사용자 평가 안내

작성: 2026-09-15. 계정·원문은 전용 로컬 평가 환경에만 있으며 공용 DB와 분리돼 있다.

## 현재 위치

① 감사 → ② 연결 확인 → ③ 기본 검사 → ④ 대표 과업·브라우저 검증 → **⑤ 사용자 평가 준비 — 현재** → ⑥ 최종 통합 판단.

Core 3개 복합 과업, 실제 브라우저 흐름, 변경 설명 및 실행 경계 검사를 통과했다. 아래는 평가 준비 자료이며, 사용자 평가를 실행했다는 보고가 아니다. 검사 범위와 한계는 29번 보고서에서 확인한다.

## 시작

1. 로컬 화면 `http://127.0.0.1:5181/login`에 접속한다.
2. 진행자가 지정한 평가 계정으로 로그인한다. 남원은 `eval-j13`~`eval-j16`, Core는 `eval-j01`~`eval-j12`다. 비밀번호와 해당 사례 주소는 Git에서 제외된 `.ci-results/user-evaluation/accounts.private.json`, `core-accounts.private.json`에 있다.
3. AI Copilot에서 **AI 상세 설명 사용**, **공고문 근거 답변 사용**을 켠다. 공개 공고·합성 프로필만 사용한다.
4. 아래 목표를 자신의 말로 설명한다. 정해진 질문 문장을 복사하지 않는다. 부족한 내용은 자연스럽게 이어 묻는다.

## 평가 목표

| 과업 | 사용자에게 줄 목표 | 사례 |
|---|---|---|
| 1. 참여 준비 | 저장된 회사 판정, 확인할 일, 제출 준비를 함께 파악하고 다음 행동을 정한다. 빠진 내용이 있으면 이어서 확인한다. | 구내식당 J05~J08 |
| 2. 근거 이해 | 저장된 결과가 왜 나왔는지 회사 정보와 공고 근거를 대조하고, AI가 확인한 사실과 아직 모르는 사실을 구분한다. | 남원 J13 또는 한림대 J09 |
| 3. 변경 영향 | 기준·현재 공고에서 실제로 무엇이 바뀌었는지 알아낸다. 원문 표현, 수집 메타데이터, 저장 분석의 차이를 구분한다. | 우치공원 J01 또는 한림대 J09 |
| 4. 제출 일정 | 실제 제출할 서류·단계·기한·방법과 예외를 확인한다. 서로 다른 제출 기한을 하나로 잘못 합치지 않았는지 원문을 연다. | 구내식당 J05 또는 한림대 J09 |
| 5. 가정 검토 | 아직 확정하지 않은 회사 조건을 가정해 해당 요건의 영향을 이해한다. 설명만으로 저장값이나 전체 판정이 바뀌지 않았는지 확인한다. | 남원 J13~J16 |
| 6. 이어서 처리 | 확인 질문의 답변을 제안하고 검토한다. 실행 전과 실행 후를 구분하며, 반영 내용과 남은 일을 다시 확인한다. 실제 입력 변경은 진행자가 지정한 미응답 사례에서만 수행한다. | 남원 J14~J16 |

J13에는 기존 사용자가 저장한 방문 완료·확인서 미제출 답변이 있다. 이를 지우거나 다시 분석해 평가 상태를 초기화하지 않는다. 이미 저장된 답변 정정 기능은 Q-010 미해결이며, 지원하지 않는 작업을 실행했다고 말하면 실패로 기록한다.

우치공원은 **002→003의 과거 비교**다. 이후 005는 취소공고이므로 현재 참여 가능한 공고로 소개하지 않는다. 계정/사례 제목에도 이 한계를 표시했다.

## 무엇을 평가할 수 있는가

- 여러 요청을 하나의 목적 안에서 처리하고 남은 항목을 이어서 찾는지.
- 저장 결과·공고 원문·가정·사용자 답변·실제 실행 결과를 구분하는지.
- 근거를 찾아 열 수 있고, 읽을 수 있는 답변을 제공하는지.
- 모르는 부분과 지원하지 않는 기능을 숨기지 않는지.

Core의 현재 저장 분석에는 원문 대비 누락·분석 결과 변동이 있다(Q-014). 따라서 이 자료로 **참가자격 정답률·판정 반전 정확도가 검증됐다고 평가하지 않는다.** 법적 업종군 관계 Q-009도 해석 보류 상태다. 이 한계는 성공 사례로 제외 처리하지 않고 별도 항목으로 기록한다.

## 진행자 기록

목표별 시작·종료 시각, 사용자의 실제 발화, 도움 횟수, 막힌 위치, 원문 확인 여부, 미해결 항목, 저장 전후 상태를 남긴다. 개발자가 중간에 질문 문장을 대신 만들어 주면 도움 1회로 센다. 턴 답변 PASS, 과업 완료, 실제 사용자 성공을 각각 기록한다.

서버를 재시작하면 대화 상태는 초기화되지만 DB의 답변·판정은 유지된다. 평가 중에는 서버를 재시작하지 않는다. 첫 사용자 평가가 끝나면 문제를 공통 원인으로 묶고, 최신 develop 차이와 함께 통합 여부를 판단한다. 이 문서는 merge나 배포 승인이 아니다.
