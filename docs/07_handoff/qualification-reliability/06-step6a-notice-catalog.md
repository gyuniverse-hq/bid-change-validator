# 6-A — 공고 목록의 저장 상태·전체 검색 범위 집계·매칭 출처 구분

부모 commit `7fdf5e5`, 브랜치 `refactor/qualification-reliability`.
6단계는 진행 중이다. 이번에는 목록/매칭을 연결했고 상세 화면의 상태 소비는 6-B로 남긴다.
실제 모델 추출 개선이나 배포 완료를 의미하지 않는다.

## 구현

### 읽기 전용 카탈로그

`GET /api/v1/qualification-notice-catalog`

선택 매개변수: `company_id`, `q`, `business_type`, `status`, `limit`, `offset`, `reference_date`.
company_id가 있으면 기존 회사 권한 검사를 먼저 수행한다. 없으면 공고 메타데이터만 제공하며
다른 회사의 검토 건/판정은 읽거나 노출하지 않는다.

- 검색어에 맞는 현재 공고 차수 목록을 만들고 그 범위에서 사업 유형을 집계한다.
- 선택 사업 유형에 해당하는 공고에서 회사의 현재 차수 검토 건을 일괄 찾는다.
- 같은 회사/공고/차수에 여러 검토 건이 있으면 `created_at, id` 내림차순의 한 건을 선택한다.
- 최신 분석, 현재 규칙의 대응 판정, 필요한 경우 재판정 사유용 과거 판정을 일괄 조회한다.
- 5단계 `_analysis_snapshot`, `_judgment_snapshot`, `select_qualification_state`를 재사용한다.
- 회사 스냅샷은 한 번 구성한다. 공고마다 상태 HTTP나 회사 조회를 반복하지 않는다.
- 상태 필터를 적용한 **후** 페이지를 나눈다. 상위 100건에서 상태를 근사하지 않는다.
- `business_counts`: q 범위. `status_counts`: q + business_type 범위(상태 필터 이전).
- 페이지 응답 `total`: q + business_type + status 범위. 화면도 이 차이를 명시한다.
- 현재 차수 없는 공고는 목록과 집계에서 동일하게 제외한다. 복수 현재 차수는 오류다.
- 데이터 연결 오류는 확인 필요 행으로 남기며, DB 조회 실패는 503이다.
- 조회 도중 최신 분석/현재 공고 차수 변경을 발견하면 409로 다시 조회하게 한다.
- `no_autoflush` 유지. 모델 호출/재판정/commit/flush/DB 스키마 변경 없음.

현재 구현은 검색 범위 메타데이터를 메모리에 모아 분류한다. 자원 보호 상한은 10,000건이며,
초과하면 422 `CATALOG_SCOPE_TOO_LARGE`로 검색어를 요구한다. 상위 일부를 전체처럼 반환하지 않는다.
대규모 데이터의 물리화된 집계/조회 성능과 운영 PostgreSQL 실행 계획은 후속 검증 대상이다.
범위 지문은 관측 결과 식별이며 DB snapshot isolation/쓰기 CAS 토큰이 아니다.

### 상태 표시 정책

- `RESULT_AVAILABLE`이고 선택된 판정 ID가 있을 때만 저장 판정을 응찰 가능/미달로 분류한다.
- 분석 불완전/실패/재판정 필요/데이터 오류는 확인 필요 묶음이고 행에 구체적 상태를 쓴다.
- 현재 차수의 Case가 없거나 분석을 안 한 경우만 미검토다. Case 부재는 분석 자체의 부재를 뜻하지 않는다.
- 과거 저장 판정이 있어도 현재 선택되지 않으면 과거 사실로 표시한다.
- legacy 분석 완전성 미확인, 기준일 미검사, 사용자 답변 최신성 미확인을 숨기지 않는다.
- `full_notice_eligibility_asserted=false`. 추출된 요건의 정확성을 새 API가 인증하지 않는다.

### 실제 프론트 연결

`app/notices/page.tsx`는 `NoticeReviewCatalog`를 렌더한다. 기존 검색/프로필/업무 단계 안내,
매칭/목록/미달 펼침/검토 열기 기능을 분리한 컴포넌트로 이동했다. 새 페이지는 기존
listNotices(limit=100) + Case별 상태 hydration을 사용하지 않는다.

- 검색 입력 초안과 제출된 검색어를 분리한다. 입력 중 이전 100건을 로컬 필터하지 않는다.
- 네 사업 유형을 항상 선택할 수 있고, 건수는 전체 검색어 범위의 서버 집계다.
- 상태 필터도 서버로 전달하며 이전/다음 페이지로 모든 해당 결과에 접근한다.
- 요청 세대/AbortController로 늦은 응답 반영을 막고 회사가 바뀌면 이전 회사 결과를 숨긴다.
- 조회 실패는 오류/재조회 버튼으로 보여준다. 0건/미검토로 변환하지 않는다.
- 상태 응답은 TS 경계에서 회사/공고/차수/집계와 연결을 검사한다.

`CachedNoticeMatches`는 부모의 선택 회사를 받고 별도 사용처에서는 기존 첫 회사 선택을 유지한다.
명칭을 **회사 기준 미리 비교**로 바꾸고 미저장 계산 결과임을 설명한다. 반환 건수와 표시 건수를
분리하고 전체 공고 집계로 표현하지 않는다. 이 단계에서 matching의 판정 로직을 바꾸지 않았다.

`openReviewTarget`은 현재 차수를 다시 확인하고 회사/공고/차수가 맞는 기존 Case를 재사용한다.
공고별 Case 조회도 페이지를 따라가며 조회 실패/불완전 목록이면 새 Case를 만들지 않는다.
동시 탭의 생성 경합까지 막는 DB 유일성/멱등성 보장은 아직 없으며 이를 주장하지 않는다.

## 이번 검증

```bash
python -m pytest -q apps/api/tests/test_notice_catalog.py
cd apps/web
node --test tests/qualification-catalog.test.cjs
pnpm exec tsc --strict --noEmit --target es2022 --lib es2022,dom lib/qualification-state.ts
```

검증 환경: Python 3.13.5, Node 22.16.0. Backend 50개 + Node 49개 = **99개 통과**.
별도로 순수 TS 상태 계약의 strict 타입 검사와 변경 Python 컴파일 검사 통과.
동일 테스트 반복 실행을 중복 합산하지 않는다.

- Backend: 실제 새 SQL/서비스/라우터 + 기존 상태 계약/스냅샷 변환 파일. SQLite 최소 ORM,
  인증·회사 로더 대역. selectinload/window query는 실제 실행. 전체 운영 ORM 검증은 아니다.
- 공고 121건에서 전체 상태 집계와 공사/응찰가능 필터, 페이지 누락/중복, 상태-상세
  순수 계약 동일성, 타회사 제외, 프로필/규칙/날짜/분석 변경, 조회 중 기준 변경을 검증했다.
- 120건의 조회에서 건별 N+1을 만들지 않는 쿼리 수를 확인했다. 실제 회사 로더의 SQL은
  대역이므로 운영 쿼리 총수/성능 수치로 사용하지 않는다.
- Node: 실제 TS 파일을 컴파일해 상태 매핑/응답 검증/요청/검토 건 재사용을 검증한다.
  네트워크는 대역이다. fixture는 위 실제 Python 서비스에 합성 DB 자료를 넣어 생성했다.
- TSX는 구문 검사만 했다. React 설치/실행, 전체 프로젝트 tsc, pnpm build, 브라우저 조작/
  시각 검수는 미실행이다. 의존성 파일과 lockfile은 변경하지 않았다.
- 원문 인용·회사 상세가 카탈로그 응답에 복제되지 않는 것을 확인했다.

## 남은 작업 (6-B)

1. 상세 화면이 새 상태를 조회하고 현재 선택 판정 ID로 표시하도록 연결.
2. 재분석/재판정/프로필 변경 후 상태·근거·현재 판정 재조회 및 늦은 응답 처리.
3. 기존 완료 문구를 처리 종료/분석 완전성/저장 판정으로 분리.
4. 실제 프론트 타입 검사·빌드·브라우저와 Copilot 병렬 작업 통합 검증.

기존 상세/Copilot은 아직 자신의 결과 선택 경로를 사용한다. 목록/상세/Copilot 전체가
이미 동일한 결과를 보여준다고 주장하지 않는다. 새 의미 그래프의 저장/전체 공고 적용도
이 단계에서 해결하지 않았다. 기본 추출/골든셋/평가기/판정 규칙/DB 스키마는 그대로다.
