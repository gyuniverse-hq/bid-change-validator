## 구현

- `ConversationState.job`에 원래 목적, 하위 요청, 근거 기준, 미해결 상태를 유지한다. 모델은 기존 요청을 삭제하거나 완료로 표시할 수 없다. 새 질문의 처리 상태와 여러 턴 과업 상태를 구분한다.
- 저장 제안은 `AWAITING_CONFIRMATION`이다. 인증된 실제 확인 API의 성공 결과와 정확한 제안 해시가 맞을 때만 `EXECUTED`가 된다. 실행 기록은 당시 요청의 처리 사실이며 현재 참가자격을 대신하지 않는다.
- 읽기 기준이 바뀌면 이전 설명은 `STALE`로 남는다. 과거 대화는 제한된 문맥 힌트만 모델에 전달하며 현재 사실은 도구로 다시 읽는다.
- 문서와 저장 판정을 함께 요청해도 장문 경로를 사용한다. 저장 근거는 완전한 fact/source 묶음으로 나누어 검증한다. 검증된 설명을 통합할 때도 모든 입력 설명의 조건·예외·기한 보존을 독립 검사한다.
- 비용 상한 내 전체 근거를 함께 읽는 경로를 우선한다. 생성 입력은 근거 번호와 인용문을 인접하게 배치하며, 모델은 서버가 열거한 fact만 고를 수 있다. source 연결은 서버가 구성하고 의미·범위 검증은 별도로 수행한다. 참조 구조가 맞는다는 사실만으로 SUPPORTED를 부여하지 않는다.
- 복합 요청에는 선택된 도구별 기준 외에 원래 요청 전체 완료 기준이 있다. 저장 확인 항목/공고 서류·일정/저장 분석 diff/회사 판정의 도구 역할을 분리했다.
- 동일한 원문 snapshot·질문 완료 기준·사용자 범위인 경우에만 앞서 검증한 문서 부분을 이어 쓴다. 현재 원문을 다시 읽고 해시를 확인하며, 미검증 부분을 우선 처리한다. 대화 메모리 범위의 캐시이고 재시작하면 초기화된다.
- 화면에서 검토 목적과 남은 항목을 볼 수 있게 했다. 저장 답변 근거의 내부 JSON을 요건별 문장으로 바꿨다.

## Q-013 — 과업 전체 근거와 완료 기준

**근거:** 작은 입력 제한으로 공고를 과도하게 분할해 호출 수와 문맥 단절이 증가했다. 분할 처리의 한계 안내가 반복 복제되어 입력 한도를 더 소모하는 결함도 확인·수정했다. 별도로 계획기가 공고 서류·일정 요청을 저장 확인 항목 도구에 배정해 공고문을 읽지 않았다. 선택된 도구별 완료만 검사하면 원래 요청의 누락을 놓칠 수 있다.

**대안:** (A) 기존 작은 분할 단위 유지와 이어읽기 강화, (B) 비용·시간 상한 안에 들어오는 공고는 전체 근거를 함께 읽고 원래 복합 목적을 검증, 더 큰 자료만 분할한다.

**권장안·반영 방향:** B. 현재 모델의 문맥 용량 안에서도 비용 상한을 별도로 적용한다. 전체 근거를 함께 읽은 생성·검증·필요시 1회 보완을 우선하고, 분할이 필요한 자료에는 검증된 부분 재사용을 적용한다. 도구별 완료 기준에 원래 복합 요청 전체 기준을 추가한다. 문서 부분 검토 완료, 요청 설명 완료, 실제 저장 실행 완료, 현실 참가자격을 각각 구분한다. 이 결정은 Q-009 법적 해석 보류를 해제하지 않는다.

## 범위와 한계

- Core 원문과 합성 프로필을 사용한 대표 복합 과업·변경 설명의 교차검증이다. 모든 공고에서 같은 품질이 보장된다는 뜻이 아니다.
- Notion의 12개 우선 시나리오는 기존 계약/DB 검사와 이번 실제 과업/브라우저 검사에 나누어 연결된다. **12개 전부를 동일한 새 과업 묶음으로 실행했다거나, 계획상의 개발40/보류24를 모두 실행했다고 보고하지 않는다.** 이미 살펴본 Core 사례는 미공개 holdout으로 부르지 않는다.
- 일부 과업은 첫 턴이 PARTIAL이고 후속 검토 후 완료됐다. 의미 검증 모델도 오류를 놓칠 수 있어 실제 결과와 원문을 함께 검수했다.
- 미완료 턴에서는 같은 도구 묶음을 다시 검토할 수 있다. 문서 이어읽기는 검증된 부분을 캐시하지만, 모든 읽기 도구의 성공 부분을 세밀하게 재사용하는 최적화까지 완료한 것은 아니다.
- 대화/과업/실행 확인 기록은 단일 서버 메모리이며 재시작 시 초기화된다. 저장 답변·판정은 DB에 유지된다.

## Q-014 — Core 저장 분석과 원문 차이의 불일치

**근거:** `copilot-db-20260914T233105Z`에서 J01~J12 × 기준·현재 총 24개 실제 제품 판정을 관찰했다. 3개 테스트는 실행·범위 검증을 통과했지만 모든 결과가 참가 불가였으며 Golden 기대값 정답 검증은 아니다. 우치공원은 각 버전 1개 요건만 판정됐다. 구내식당은 기준 3개/현재 2개, 한림대는 기준 3개/현재 2개 요건만 판정됐고 동일 공고 내 4개 프로필 결과가 같았다. 한림대의 대응 원문 4개는 동일하지만 저장 분석 diff는 4건이다. 원문 변경과 추출·구조화 결과 변동을 혼동하면 잘못된 변경 설명이 된다.

**대안:** (A) 저장 분석을 정답으로 간주해 데모, (B) 실제 저장 결과를 투명하게 설명하고 원문 대조를 별도로 제공하며, 판정 정답 평가는 원문·구조화 요건의 검수 후 수행.

**권장안:** B. 원문/메타데이터 비교를 READ_CHANGES에 연결한다. 부족한 저장 분석을 임의로 보완한 정답으로 덮어쓰지 않는다. 사용자 평가에서 원문 설명·여러 턴 과업 수행은 평가할 수 있지만, Core 12개 참가자격 정답률이나 판정 반전 시연은 현재 자료로 완료 판정할 수 없다. 이 한계는 챗봇 대화 처리와 별개인 분석 입력 검수 작업으로 남긴다.
