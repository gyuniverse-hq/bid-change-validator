# 노션 과업 기준 대비 구현·검증 차이표

작성: 2026-09-15 KST. 조사 기준 코드: `156e3fa4848775b2b80934888090779cb3a30778`, `codex/ai-copilot-evaluation-ready`.

**결론:** 도구 조합·근거·대상·명시 확인 계약은 재사용할 수 있다. 그러나 최근 질문별 분기 추가와 재시험을 전체 사용자 과업 검증으로 대신했다. 다음 우선순위는 개별 질문 패치가 아니라 목적·미해결 요구사항의 유지, 근거 충분성에 따른 보완, 통합 답변 및 여러 턴의 완료 평가다.

이번 산출물은 설계·코드·기존 로그의 대조다. 제품 코드 변경, 새 테스트 실행, 모델 호출, DB 조회/변경, 원격 develop 갱신·비교는 하지 않았다. 기존 검사 기록을 이번 실행으로 재분류하지 않는다.

## 1. 기준과 진행 상태 정정

읽은 설계:

- [챗봇 3차 개선 정리](https://app.notion.com/p/3dae94b44d07805b8d19cc5b9c28c4e6): 최신 v3.1 지침을 아래 과거 질문별 패치 이력보다 우선한다.
- [기본 설계 v3.1](https://app.notion.com/p/3dae94b44d0781e1ba5bedf81822f619): §4 사용자 목적, §6 조정자·충분성 루프, §7 계약, §10 과업 검사, §13 대표 복합 대화.
- [구현·평가 계획 v3.1](https://app.notion.com/p/3dae94b44d07814bac73cb2e9a93abcc): §3 C01~C08, §4 고정 비교 조건, §5 개발/보류 평가, §7 12개 시나리오, §8 W0~W6.

노션의 설계 요구를 기준으로 삼되 그 페이지의 과거 구현 진행 상태를 현재 코드 사실로 사용하지 않는다. 노션은 이번 작업에서 수정하지 않았다.

| 전체 순서 | 이번 조사 후 표기 |
|---|---|
| ① 감사 → ② 연결 → ③ 기본 검사 | 수행 이력 존재. W0~W6 전체 완료라는 의미는 아님 |
| **④ 과업 단위 통합 검증 — 현재** | 설계 차이 확인 및 재사용/보완 순서 확정 |
| ⑤ 정식 사용자 평가 | 진입 전. 지금까지의 사용자 실행은 개발 중 탐색 평가로 보존 |
| ⑥ 최종 통합 판단 | 미진행. 과업 평가·미해결 설계·최신 develop 차이 확인 필요 |

**용어:** 여기서 job은 사용자가 달성하려는 목적이며, 한 질문·도구 호출·원문 조각·테스트 함수와 다르다. 새 Job DB 테이블이나 그래프 라이브러리 도입을 노션의 필수 요구로 해석하지 않는다. 과업을 여러 턴에서 유지할 수 있는 상태와 완료 기준이 필요하다는 구현 제안이다. 메모리 저장은 노션이 허용한 데모 선택이므로 DB 영속성 부재 자체를 설계 위반으로 판정하지 않는다.

## 6. 먼저 완성할 대표 job

**목적:** 선택한 공고를 회사 기준으로 검토하고, 부족한 점과 제출 준비를 근거에 따라 파악한다. 시작 질문을 한 문장으로 외우게 하지 않는다. 기존 J05 합성 replay는 계약 개발용으로 유지하고, 남원 자료는 아래 한계를 가진 실제 원문 평가용으로 사용한다.

| 요구 ID | 사용자가 얻어야 할 결과 | 완료 근거/금지되는 오판 |
|---|---|---|
| R1 | 현재 저장 판정과 직접 원인 | 고정된 회사/버전/판정 snapshot. 엔진 결과와 실제 자격 확정을 구분 |
| R2 | 회사정보와 원문 비교·확인 필요 | 근거의 값/예외와 회사 값 대조. Q-009 관계는 확정하지 않고 한계로 유지 |
| R3 | 본인이 답할 항목과 수동 검토 구분 | askability 및 원문 근거. 질문 목록과 조건별 입력 필드를 혼동하지 않음 |
| R4 | 새 정보의 가정→제안→확인 결과 이해 | 확인 전 쓰기0, 확인 뒤 API/DB 결과, 새 판정 조회. 미지원 정정은 완료 불가로 표시 |
| R5 | 서류·제출 단계·기한·방법 파악 | 검수된 원문 근거. 입찰/현장/계약/이행 구분, 불명확한 기한을 추정하지 않음 |
| R6 | 남은 일·이유·근거를 후속 대화에서 확인 | 앞선 요구 ID/대상과 연결. 마감일 재질문 때문에 미해결 자격·확인서가 사라지지 않음 |

시나리오 패키지는 시작 snapshot·필수 결과·금지 주장·허용 상태 변화·중단 조건을 고정한다. 발화 순서, 동의어, 두 요구의 합침/분리, 주제 이탈 후 복귀를 변형한다. 동일 원형의 변형은 독립 job 수로 부풀리지 않는다. 실제 모델 응답 후 사람이 기대 결과를 검수한다.

**평가 구분:** 응답의 processing PASS는 그 턴의 결과다. job PASS는 요구한 R항목을 모두 만족하고 핵심 오류·거짓 실행이 없을 때만 부여한다. 모르는 것을 정확히 설명한 것은 안전성 성공일 수 있어도, 사용자가 요구한 결론을 못 얻었다면 job 완료와 다르다. Q-009처럼 외부 해석이 필요한 경우 과업 수준의 제한을 명시하고 완료율에서 임의 제외하지 않는다. 저장값·원문·시스템 상태가 다른 시나리오를 같은 Before/After로 비교하지 않는다.

## 7. 구현 순서와 완료 관문

| 순서 | 공통 작업 | 완료해야 다음 단계로 이동 |
|---|---|---|
| A — 다음 작업 | 기존 ConversationState 위에 목적/요구/미해결 상태와 상태 전이 계약 구체화. 원 요청·현재 요청·완료 기준 분리 | 대표 job의 시작/추가/정정/가정/주제 전환/기준 변경을 모델 없이 재생. 원래 요구가 조용히 누락되지 않음 |
| B | 계획·근거 충분성·보완 읽기 연결 | 누락된 요구 ID에 맞춰 필요한 도구만 재조회. 예산 안에서 충분성 판단; 전체 읽기만 반복하지 않음 |
| C | 검증된 결과를 요구별 통합, 답변과 후속 대상 생성 | 중복·내부 JSON·부분 부재 문장·기한 충돌 제거, 근거 및 미완료 요구 보존. Q-011은 이 작업의 서류 사례 |
| D | 12개 우선 시나리오를 고정 데이터와 실제 경로로 묶음 실행 | 계약/mock, 실제 DB, 실제 모델, 브라우저 결과를 분리. 턴 상태와 job 상태 둘 다 기록 |
| E | 개발/보류 평가 분리·비용 계획 후 Core 교차검증 | 보류 사례에 맞춘 즉석 패치 금지. 실패 유형을 공통 구조로 환류 |
| F | 정식 사용자 평가 → 통합 판단 | 사용자에게 목표만 제공. 도움 횟수/시간/막힘 기록. 이후 최신 develop 비교 |

공용 DB 변경·기존 작업 삭제·main/develop 수정·merge·배포는 이 계획의 승인 범위에 포함하지 않는다. 실행 예산은 기존 승인 범위를 존중하고 새 평가 묶음의 비용부터 계산한다. 이번 차이표 작성에는 모델 비용이 발생하지 않았다.

## 8. Q-012 — job 상태와 완료 기준의 명시화

**근거:** 기본 설계 §7은 목표·미해결 질문·가정을 대화 상태로 관리하도록 요구한다. 현재 ConversationState와 턴 단위 task_status만으로는 여러 턴의 요구 완료를 구분하기 어렵다. 이는 기존 설계의 누락된 구현을 구체화하는 문제다.

**대안 A:** 최근 대화 텍스트를 모델에 주고 매 턴 목표를 다시 추론한다. 변경은 적지만 미해결 누락·완료 기준 변동을 검증하기 어렵다.

**대안 B / 권장:** 기존 상태에 stable goal/requirement 식별자, 요구별 미해결·근거충족·사용자확인대기·외부확인필요 상태, 근거 scope/fingerprint, 허용된 추가/철회 이력을 둔다. 원래 요청과 새 요청을 분리하고 변경된 기준에 의존한 결과만 무효화한다. 모델은 변경안을 제시하고 서버가 범위·전이를 검사한다. 정확한 필드명과 저장 형태는 구현 계약에서 정한다.

**대안 C:** 새 영속 Job 테이블·별도 실행 플랫폼을 먼저 도입한다. 복원에는 유리하지만 현재 목적 이해/통합 답변 결함의 선행 해결책은 아니며 DB 협의가 추가된다.

**설계 대화 전달문:** “기존 ConversationState에 과업 요구별 상태와 기준을 추가하고, 턴 응답 PASS와 전체 과업 완료를 분리하려 합니다. 새로운 Job DB를 먼저 도입하지 않고 기존 조정자·도구·명시 확인 경계를 재사용하는 B안을 권장합니다. 기존 요구의 철회/변경 및 외부 확인 필요를 과업 완료율에 반영하는 기준을 함께 검토해 주세요.”

이 질의를 보냈거나 합의했다고 기록하지 않는다. 기존 설계가 이미 요구한 통합 답변·묶음 검증 자체를 새 승인 전까지 막는 사유로 사용하지 않는다. Q-009 원문 해석, Q-010 저장 답변 정정 정책은 별도 미해결로 유지한다.
