## 이번 첫 구현

`apps/api/app/ai/qualification/extraction/review_coverage.py`

- 기존 canonical source block을 검토 후보로 등록한다. 키워드가 없다고 후보를 제거하지 않는다.
- 실제 document_id / block_index / 차수 / 선택 원문 지문으로 후보 ID를 만든다.
- 원문과 블록 내부 문자 구간을 그대로 보존한다. 숫자 위치를 LLM이 계산하지 않는다.
- 응답의 누락, 중복, 알 수 없는 ID, 잘못된 상태, 미해결, 추가 문맥 필요를 구분한다.
- 빈 결과를 자동 성공으로 처리하지 않으며, 중복 응답에 마지막 값 우선 정책을 적용하지 않는다.
- DB 접근, 모델 호출, 기존 API/판정/Copilot 경로 변경은 없다.

후보 응답 형태:

```json
{"candidate_id": "CAND-<hash>", "status": "UNRESOLVED", "reason": "AND/OR 관계 추가 검토 필요"}
```

상태는 REQUIREMENT / NOT_REQUIREMENT / UNRESOLVED / NEEDS_CONTEXT다.
REQUIREMENT 이외에는 사유가 필요하다. 처리되지 않은 후보는 서버가 누락 목록으로 남긴다.
REQUIREMENT의 실제 원자 조건·근거·관계는 후속 해석 계약에서 검증한다.

### 이번 구현이 보증하지 않는 것

- 후보는 아직 **블록 단위**다. 블록 내 독립 조항 분할과 상위 조건·각주 연결은 후속 작업이다.
- 전달된 블록 범위의 처리 내역을 검사한다. 파서나 검색기가 원문을 놓치지 않았다는 보증은 아니다.
- `COMPLETE`는 처리 내역의 완결성이다. 정답·분석 완료·참가 가능을 뜻하지 않는다.
- 모든 후보를 NOT_REQUIREMENT라고 잘못 분류하면 의미 검증이 따로 필요하다.
- ID는 동일 입력의 재현용이며, 버전 간 동일 요건 연결 키가 아니다.
- offset은 전달받은 block.text의 Python 문자 위치다. PDF 바이트 위치나 문서 전역 위치가 아니다.
- 현재 서비스의 추출 함수에는 아직 연결하지 않았다. 이 commit만으로 제품 성능이 개선됐다고 보고하지 않는다.

## 다음 구현 순서

1. 원문 블록/조항의 부모·각주 문맥을 보존하는 후보 목록과 실제 요청 범위 기록.
2. 후보 ID별 응답을 받는 추출 전략을 선택 기능으로 연결하고 미응답 후보만 재처리.
3. 원문 구간 참조와 조건 역할 검증. 공고 어디에나 있는 값을 무관한 요건에 붙이지 않기.
4. AND/OR/예외/같은 실적에 적용되는 복수 조건 보존, 그룹을 잃지 않는 중복 정리.
5. 실행 상태/검토 완전성/판정 상태/유효성 분리와 서비스 공통 결과 선택 정책.
6. 목록 필터·집계 범위 정리 및 상세·변경 재검증·Copilot 통합 검증.

각 단계에서 기존 경로와 새 경로를 같은 입력으로 비교한다. 전체 구조를 한 번에 대체하지 않는다.
