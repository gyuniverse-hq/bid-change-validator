# Job·질문 선택형 챗봇 전환 의견과 현재 작업 정리

> **후속 결정:** 사용자가 초기 메뉴를 변경 공고 대응·입찰 참여 준비 두 개로 축소했다. 참여 준비 순서는 서류·기한·방법 → 준비 순서 → 미확인 항목이다. 아래 네 메뉴는 이전 제안으로 보존하며, 구현 범위는 [48번 새 채팅 인계](48-two-job-new-chat-handoff.md)가 우선한다.

2026-09-16. 사용자의 “정해진 Job을 먼저 표시하고, 그 안에서 검증된 질문을 선택하도록 하자”는 제안에 대한 검토다. 이 문서의 새 메뉴·질문 카탈로그는 아직 구현하지 않았다.

## 권장 결정

현재 자유질문 경로의 반복 보완을 마무리하고, 현재 코드·검증 결과를 보존한 뒤 Job·질문 선택형 평가 UI로 범위를 전환하는 것이 적절하다. 전체 검증 완료·merge 가능으로 마감하는 것은 아니다. 현재 상태는 `NOT_READY`이며, 공통 기능과 로컬 자료를 재사용할 수 있는 구현 체크포인트다.

질문 버튼만 기존 자유질문 API에 전달하면 동일 문제가 남는다. 서버가 Job·질문 ID에 따라 읽을 자료, 설명 범위, 산출물, 완료 조건을 고정해야 한다. 모델은 근거를 읽고 그 범위 안의 답변을 작성한다. 메뉴 밖의 업무를 추가 완료 조건으로 만들지 않는다.

## Q-052 — 제한된 Job을 매번 자유질문으로 재계획하는 문제

**근거:** 최신 v35 N3는 운반 예외를 설명하는 흐름에서 처리 완료 후 증빙 제출까지 완료 조건에 포함하며 4회 후에도 OPEN이었다. C1도 등록·계약 단계 서류와 미확인 항목을 합성하는 과정에서 4회 후 미완료였다. C2 첫 답변은 현재 저장 판정과 전후 비교 기록 부재를 실제로 설명했지만 진행 상태에는 해당 설명 누락이 남았고, 본문에 `[F1]` 같은 내부 참조도 노출됐다. N4는 명시 저장·새 판정 조회가 성공해도 기존 Job 기준 변경으로 OPEN이 남는다. 사실·출처 검증뿐 아니라 질문 범위와 상태 계약을 고정할 필요가 있다.

**대안:** (A) 자유질문 계획·완료 프롬프트를 계속 보완한다. 자유도는 크지만 검증 범위가 계속 늘어난다. (B) 질문 버튼만 만든다. 진입은 쉬워져도 같은 계획기에서 범위가 달라질 수 있다. (C) 서버 Job·질문 카탈로그를 고정하고 검증된 흐름만 UI에 노출한다. 초기 지원 범위는 좁지만 검증 대상과 종료 조건이 분명하다.

**권장안:** C를 첫 사용자 평가 범위로 채택한다. 기존 자료 검색·판정 조회·출처 검증·명시 실행은 재사용하고, 범위가 바뀌는 계획·완료 계층을 카탈로그 계약으로 제한한다. 현재 실패를 숨겨 해결로 취급하거나 성공 문장을 정답 템플릿으로 저장하지 않는다. 새 선택형 UI 구현은 후속 작업이며 이번 체크포인트에서 완료했다고 보고하지 않는다.

## 제안하는 메뉴

현재 7개 검증 Job은 회사·공고의 차이를 확인하는 시나리오다. 사용자 메뉴 7개를 뜻하지 않는다.

| 사용자 Job | 선택 질문 흐름 | 기존 검증 시나리오 |
|---|---|---|
| 변경공고 대응 | 무엇이 바뀌었나 → 우리 회사 영향 → 원문과 해야 할 일 | N1·N2·C2·C3 |
| 입찰 참여 준비 | 조건·서류·기한·방법 → 미확인 항목 → 실행 체크리스트 | C1 |
| 조건·예외 확인 | 선택 요건의 판정 이유 → 예외 조건 → 확인 근거·자료 | N3 |
| 추가답변 반영 | 답변할 조건 → 비저장 예상 영향 → 제안 검토 → 명시 저장 → 결과 | N4 |

이는 제안 분류이며 실제 노출 범위는 검증 결과로 결정한다. 예를 들어 C1의 복합 준비 흐름이 미완료라면 그 질문을 정상 제공 목록에 넣지 않는다. 숨기는 것만으로 결함이 해결됐다고 기록하지 않는다.

## 구현할 계약

카탈로그 한 항목에는 `job_id`, `question_id`, 계약 버전, 사용자 표시 문구, 대상 요건/공고 선택값, 필요한 데이터, 고정 조회 도구, 답변 형식, 완료 기준, 검증 근거와 노출 상태를 둔다.

- 질문의 실제 공고·회사·차수·판정·문서 기준은 서버가 읽는다. 테스트 기대 답변이나 Golden 결과를 제품 응답에 주입하지 않는다.
- UI와 API가 같은 노출 상태·선행 조건을 사용한다. UI에서 숨겼다고 권한 검사가 없어지는 것은 아니다.
- 비교 판정이 없으면 전후 판정 비교 질문을 비활성화하거나 선행 작업을 안내한다. 미확정 법적 해석은 “확인 필요”로 설명하는 것이 정상 결과이며, 적격으로 바꾸지 않는다.
- 선택 요건 설명은 해당 요건과 필요한 관련 근거를 읽는다. 다른 계약·제출 절차는 질문의 완료 조건으로 덧붙이지 않는다.
- 설명 완료, 실제 회사 자격, 답변 저장 성공을 별도 상태로 표시한다.
- 추가답변은 정해진 필드와 증빙 보유 선택을 사용한다. 가정·제안은 저장하지 않고, 검토 화면의 명시 실행을 유지한다.
- 기본 답변은 질문의 결론·핵심 근거·다음 행동을 중심으로 표시하고 상세 근거·검토 상태는 접는다.
- 자유입력은 첫 평가에서는 주 진입 경로로 두지 않는 안을 권장한다. 허용 여부는 별도 제품 선택이며 이 문서만으로 제거하지 않았다.

## 검증과 노출 기준

한 번 답변이 좋았던 문장을 승인 질문으로 간주하지 않는다. 질문 ID 자체가 아니라 Job의 이어지는 흐름, 적용 가능한 데이터 상태, 코드·계약 버전을 함께 검증한다.

1. 모델 없이 카탈로그·선행 조건·권한·출처 범위·저장 경계를 검사한다.
2. 대표 공고·회사 자료에서 한 Job의 질문을 같은 대화로 순서대로 실행한다. 이미 검증한 자료를 재사용하고 동일 호출을 API·브라우저에서 중복하지 않는다.
3. 실제 원문·판정·화면을 대조해 사실, 요청 범위, 후속 연결, 완료 상태를 함께 확인한다. 모델 자체 PASS만으로 노출하지 않는다.
4. 장문 준비와 실제 저장처럼 위험이 높은 흐름만 추가 확인한다. 다른 공고·상태에서 미검증이면 노출 범위를 제한한다.
5. 의미·출처·저장 계약이 바뀌면 영향을 받는 질문을 검증 대기로 돌린다. 실패·미실시는 실패·미실시로 남긴다.

UI 선택 방식은 모델의 잘못된 사실 생성 자체를 없애지 않는다. 기존 출처 검증, 서류별 의무 구분, 회사·차수 경계, 명시 실행 검사는 계속 필요하다.

## 현재 작업을 어디까지 정리할지

계속 실행 중이던 Job의 결과 수집과 최종 데이터 보존 확인을 마쳤고, 새 고비용 Job은 pause 표식으로 보류했다. 현재 후보에서 N3와 C1은 허용된 후속 질문까지 수행해도 미완료이며 C2 품질 문제도 남아 G4에 진입하지 않는다. 현재 코드의 전체 사용자 평가 준비 완료를 선언하지 않는다.

재사용 대상은 LangChain 검색·프롬프트·모델 경로, 문서 인덱스, 남원 네 회사 입력 명세, 판정·근거 조회, 제안과 명시 실행, 실행 후 판정 조회, 접힌 진단 UI, 검증 증거 수집기다.

실패를 남길 대상은 자유질문에서 작업 범위가 확장되는 문제, 복합 제출 의무의 완료 판정, 일부 답변의 긴 대기·반복이다. 현재 최종 상태와 데이터 보존 확인은 45번 보고서와 로컬 `status.json`을 따른다.

다음 작업 순서는 **Job·질문 목록 및 답변 범위 확정 → 서버 카탈로그와 선택 UI 연결 → 고정 흐름 검증 → 통과 범위만 사용자 평가 → 최신 develop 대비 최종 통합 판단**이다. 공용 DB 적용·merge·배포는 포함하지 않는다.
