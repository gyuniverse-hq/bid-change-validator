## 실제 발견과 수정

1. **소재지 요건 매칭 오류:** 추출 키와 선두 `○`가 함께 달라져 같은 지역 조건이 ADDED/REMOVED로 분리됐다. 조건 식별에만 선두 글머리표를 제거했다. 원문 비교값에는 남겨 MODIFIED로 재검증하며, 다른 법적 조건을 같은 것으로 합치지 않는다.
2. **새로고침 후 비교표 소실:** 재검증 결과가 DB에 저장됐지만 화면은 메모리의 작업 결과만 읽었다. 사례 권한을 검사하는 GET 조회를 추가하고 저장된 결과를 읽도록 연결했다. 현재 사례·기준 분석·현재 분석·결과 판정 ID가 모두 일치해야 현재 비교표로 표시한다. 조회는 재실행하지 않는다.
3. **기존 화면 검사 데이터 노후화:** 추가 실행한 `case-workspace.test.cjs` 3개가 v0.3을 현재 규칙으로 간주해 실패했다. 실제 제품 규칙 v0.4에 맞게 fixture를 갱신하고 v0.3 거부 검사를 유지했다. 제품 규칙을 낮추지 않았다.

준비 스크립트의 회사 relationship 조회 오류와 브라우저 검증기의 action 사례 ID 위치 오류도 실행 전에 발견해 수정했다. 이 두 실패는 제품 실패와 구분한다.

## Q-015 — 변경이 회사 판정에 미친 영향을 어떤 자료로 완료 판단할 것인가

**근거:** 후속 질문은 판정 전후의 인과관계를 묻는다. 이번 실제 실행은 READ_CHANGES + READ_JUDGMENT + READ_CHECKS를 사용했다. 현재 1227 충족은 답했지만 기준 판정의 1224 상태와 회사의 기준 snapshot을 통합해서 비교하지 않아, 답변 말미에 회사별 비교 자료가 제시되지 않았다는 설명과 반복이 붙었다. DB에는 재검증의 source/result 판정 ID와 프로필 snapshot이 이미 있다. 검증기가 PASS를 내도 이 제품 기대까지 충족했다고 볼 수 없다.

**대안 A:** 현재처럼 요건 diff와 현재 판정만 설명하고, 전후 영향은 확인 불가로 명시한다. 구현은 적지만 사용자가 기대하는 변경 영향 설명을 끝내지 못한다.

**대안 B — 권장:** 하나의 변경 영향 작업에서 저장된 재검증 ID를 기준으로 양쪽 판정·적용 규칙·기준일·회사 snapshot을 함께 읽는다. ‘변경 조건 / 재판정 결과 / 기존부터 남아 있는 미달 / 해석 보류’를 묶어 완료 기준으로 검증한다. 자료가 다른 기준이면 영향 단정을 보류한다. 기준 판정이나 원문을 추정하지 않는다.

**권장 검증 기준:** 이 사례에서는 1227 현재 충족과 별도 조달 등록 미달을 먼저 설명하고, 실제 기준 판정도 조회해서 판정 반전 여부를 비교한다. 이미 확인한 코드·상태를 반복하거나 불필요한 예외 검토로 범위를 늘리지 않는다. Q-009 해석은 별도 보류다. 설계 대화로 전달할 수 있는 검토안이며, 외부에 전송하거나 합의 완료 처리하지 않았다.
