## 무엇이 제품에 연결됐나

기존 내부 `review_v1` 경로를 아래 흐름에 연결했다.

```text
상세 화면에서 새 분석 방식 선택
→ POST qualification-analysis {extraction_strategy: review_v1}
→ 서버의 기능 활성화 상태 확인
→ 원문 스냅샷/후보 계획/누락 재처리/근거 검사/기존 canonical 변환
→ 기존 분석·요건·근거 테이블에 새 실행 저장
→ 회사 판정 API
→ qualification-state가 선택한 분석/판정/근거 재조회
→ 목록과 상세의 공통 상태 표시
```

`review_v1`은 기존 슬롯형 저장 계약에 맞는 조항별 누락 검사 경로다.
**`review_graph_v1`의 복합조건 그래프와 같은 경로가 아니다.** 이번 API는 graph 모드를 받지 않는다.
AND/OR/예외의 공고 전체 적용과 그래프 저장/판정/변경 비교는 아직 내부 구현과 제품 경로 사이에 남아 있다.

## API·활성화

기존 POST의 본문이 없으면 여전히 `legacy`다. 알려지지 않은 필드/경로는 422이며,
서버 비활성 상태의 `review_v1`은 모델이나 DB 실행 전에 409로 거절한다.

```http
GET /api/v1/qualification-analysis-options
POST /api/v1/notices/{notice_id}/versions/{version_number}/qualification-analysis
Content-Type: application/json

{"extraction_strategy":"review_v1"}
```

서버 환경변수 `QUALIFICATION_REVIEW_V1_ENABLED=true`를 명시하고 API 프로세스를 재시작해야 활성화된다.
Settings 기본값은 false다. 실제 배포 설정은 이번 작업에서 변경하지 않았다.
Docker를 사용하는 경우 호스트 .env만 고치는 것으로 컨테이너 환경에 전달됐다고 가정하지 말고,
API 서비스의 환경 전달 설정과 위 options 응답을 확인한다.
기존 인증 미들웨어와 접근 경계는 유지했으며 새 인증 우회 경로를 추가하지 않았다.

화면은 서버가 알려준 허용 경로만 활성화한다. 조회 실패 시 새 모드를 임의 활성화하지 않는다.
과거 분석에 경로 기록이 없으면 `미확인`으로 표시한다. 새 방식을 명시적으로 선택했을 때
기존/미확인 분석을 새 방식 결과로 재사용하지 않는다. 회사 재판정은 방식 선택과 무관하게
현재 분석을 사용하며 LLM을 다시 호출하지 않는다.

새 분석은 비용이 발생하고 해당 공고 차수의 최신 분석을 바꾼다. 실험은 격리된 환경에서 진행하는 것이 좋다.
비교 실측만 필요할 때는 기존 READ ONLY 반복 측정기를 사용한다. 이 POST는 실제 저장 경로다.

## 입력·저장 기준 보호

- 원문/모델 응답을 메타데이터에 복사하지 않고 입력 해시·문서 해시·실행 방식·모델·예산을 기록한다.
- 첨부 순서는 문서 ID로 고정하며 블록 내부 순서는 보존한다.
- 추출 실패/미처리 첨부가 입력에서 제외됐으면 review 결과에 경고를 추가하고 SUCCEEDED를 PARTIAL로 낮춘다.
- 모델 호출 후 원문과 추출 상태를 다시 읽어 변화를 확인하면 결과 저장 전에 409로 중단한다.
- 이 전후 비교는 compare-and-swap 잠금이나 전체 동시성 격리를 보장하지 않는다.
- 결과는 새 분석 실행으로 저장하며 기존 분석을 덮어쓰지 않는다.
- `extraction_strategy` 및 `execution_basis`는 기존 분석 상세 응답에 추가한 선택 필드다.
- 이미 존재하는 진단 JSON 저장을 사용한다. DB 스키마/마이그레이션은 바꾸지 않았다.
- 요청 경로와 저장 응답 경로가 다르면 후속 회사 판정을 시작하지 않는다.
- 분석 실패/0건은 후속 판정으로 보내지 않는다. POST 결과 불명/GET 실패의 자동 쓰기 재시도도 없다.

제품 review 옵션: 후보 누락 재시도 1회, 호출 24회, 호출 사이 경과시간 예산 180초.
OpenAI client의 timeout 60초/max_retries=0을 사용한다. timeout과 호출 사이 예산은
전체 wall-clock의 엄격한 180초 종료 보장이 아니다. 코드 상한은 API 금액 상한과도 다르다.

### Backend 저장 왕복 테스트

모델 I/O만 합성 응답을 넣고, 실제 분석 서비스/정규화/canonical 변환/ORM/저장과 읽기를 사용했다.
POST review_v1 → 201 → GET 동일 실행·경로·진단 확인 → 실제 회사 판정기 → 저장 판정 →
공통 상태와 카탈로그의 결과 일치를 검사했다. 뒤이어 legacy 실행을 저장해도 이전 review 실행이
덮이지 않는 것을 확인했다. 입력은 합성 지역 조건 한 건이므로 복합조건/실공고 성능 보증은 아니다.

### Browser 테스트

기존 6흐름(서버 필터, 판정/근거, 재판정 시 재추출 금지, 오래된 기준 표시, 저장 후 조회 실패 복구,
503 구분)에 새 경로 선택을 추가했다. 서버 비활성 옵션을 확인하고, 합성 서버 활성화 후
review_v1 선택 → 분석 POST의 전략 확인 → 판정 POST → 저장된 review_v1 표기를 검증했다.
브라우저 전체 합성 POST 건수는 분석 1회/판정 3회였다.
HTTP 자료를 가로채는 UI 테스트이므로 위 PostgreSQL 저장 테스트와 별도다. 운영 E2E로 합쳐 표현하지 않는다.
