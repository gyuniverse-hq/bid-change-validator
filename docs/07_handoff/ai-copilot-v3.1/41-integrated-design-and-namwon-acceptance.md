## Job의 완료 의미를 먼저 바로잡기

예: “우리 회사 참여조건, 부족한 점, 제출서류·마감·방법, 준비 순서”를 한 Job으로 관리한다.

고정할 산출물은 ① 회사와 조건 비교 ② 추가 확인 및 행동 ③ 서류별 기한/방법 ④ 준비 순서다. 후속 질문은 이 목록 중 필요한 부분을 이어가거나 새로운 산출물을 추가한다. 사용자 요청으로 범위가 바뀐 경우에만 변경 이력을 남기고 조정한다. 모델이 이번에 READ_CHECKS 하나를 선택했다고 최초 제출서류 요청을 지우면 안 된다.

다음 상태를 서로 구분한다.

- 답변으로 설명이 확인된 항목
- 아직 자료를 찾거나 설명을 보완할 항목
- 회사 답변/기관 확인이 필요한 항목과 구체적인 이유·다음 행동
- 지원되는 실제 저장/재판정 요청과 실행 결과

사용자가 “무엇을 확인해야 하나”라고 물었으면 질문·이유·행동을 충분히 제공하는 것으로 해당 설명 요청은 끝날 수 있다. 사용자가 실제로 기관에 연락하거나 증빙을 확보해야만 설명 완료가 되는 구조는 피한다. 반대로 “회사 자격을 확정해 달라”는 요청에서 근거가 없으면 판정은 보류다. `설명 완료`, `남은 외부 확인`, `실제 실행 완료`를 화면과 상태에서 구분한다.

새 질문이 들어왔다고 예전 질문으로 강제 회귀시키지도 않는다. 최초 목적, 현재 요청, 새로 추가한 범위, 보류 이유를 별개로 관리해야 한다.

## 가이드와 자연스러운 챗봇을 함께 충족하는 연결

준비 경로: 원문/차수 확정 → 추출/청크/위치 metadata → 변경분 임베딩 → 차수별 인덱스/manifest → 준비 완료 확인.

질문 경로: 사용자·회사·차수 확인 → Job에서 필요한 산출물 선택 → 저장 판정/프로필 조회와 LangChain 문서검색 → 예외/각주/누락 범위 보완 → 검증된 업무 사실 묶음 → 질문에 맞는 답변 생성 → 상태/주장/Job 검사 → 답변 및 남은 일 기록.

기존 FAISS·추출/판정 엔진·인증·예산·출처·명시 확인 API는 재사용한다. 벡터 저장소 교체나 LangGraph 전면 전환은 필수 전제가 아니다. 모든 DB 조회와 판정 계산을 LangChain으로 바꿀 이유도 없다.

특정 사실은 관련 근거를 좁게 검색한다. 넓은 질문은 자격·서류·일정·예외 범위를 확인하고 부모 섹션/연결 조항을 보완한다. k=4 고정만으로 전체를 읽었다고 하지 않으며, 반대로 “준비”라는 단어만으로 전체 269 records를 매번 모델에 넣지 않는다. 범위별 FOUND/NOT_FOUND/NOT_APPLICABLE/UNAVAILABLE 의미를 보존한다.

제출 의무는 문서명만이 아니라 주체·단계·기한·방법·조건·근거를 연결해 유지한다. 동일 문서가 입찰/계약 두 단계에 필요하면 별도 의무다. 일정은 절대 날짜/상대 사건/미확정을 구분하고 준비 선후 관계를 명시한다. AI가 구조를 만들었다는 사실과 검증됐다는 사실은 구분한다.

One/Few-shot 예시는 답변 형식, 부정/예외 보존, 회사정보와 원문의 구분을 학습시키는 용도로 사용한다. J13~J16의 기대 상태를 모델 프롬프트에 정답으로 주입하고 맞혔다고 평가하지 않는다. 판정 기대값은 평가기/검수 자료에 두고 실제 답은 원문·프로필·실행된 판정에서 만들어야 한다.

기존 동일 기준 원문/검증 결과는 항목 단위로 재사용하되 회사·공고·분석·규칙·문서 기준이 달라진 관련 항목은 다시 확인한다. 후속 질문이 표현만 달라졌다는 이유로 전체 작업을 처음부터 다시 하거나, 반대로 옛 사실을 현재로 재사용하지 않는다.

이 네 패턴은 두 방향 변화, 예외에 의한 유지, 미확인 유지라는 서로 다른 실패 가능성을 검사한다. 그러나 '네 회사에서 숫자가 같음'만으로 합격하지 않는다. J16은 원문 해석 보류나 데이터 오류 때문이 아니라 직접 운반 예외의 회사 정보가 없어서 확인 필요여야 한다. 판정 사유·askability도 기대값에 포함한다.

## 남원 자료에 추가로 필요한 명세

1. **현재 로컬과 v03을 구분한다.** `local_copilot_evaluation.py`는 v02 bundle을 읽고 `scenario_facts_not_imported_as_answers`를 기록한다. 시나리오 추가정보가 자동 답변으로 적재되지 않는다. 기존 사용자 J13의 확인서 미제출 답변도 보존해야 하므로 별도 v03 이름/사례가 필요하다. 같은 J13 라벨만으로 입력 일치를 주장하지 않는다.
2. **프로필/공고별 답변/검수 metadata를 분리한다.** 소재지·업종은 회사 정보, 방문 확인서·해당 폐기물 운반 예외는 공고별 확인 사실, '해석 검수 완료'는 원문·규칙의 검수 metadata다. 회사 속성으로 해석 승인을 넣지 않는다. 법적 허가·적합 장비를 별도 필드로 받는 제품 계약과 Excel의 복합 '예'를 어떻게 연결하는지 명세가 필요하다. 차량 보유 하나로 축약하지 않는다.
3. **아니오와 미입력을 보존한다.** 예외 false와 unknown은 다른 판정 경로다. UI 입력→API→DB→판정에서 null/false 변환을 확인한다.
4. **판정 범위를 명시한다.** Golden Notion은 일부 조건 충족을 전체 참가 가능으로 표시하지 말라고 한다. 그러나 데모 표에는 참가 가능/불가 반전 문구도 있다. Excel 네 핵심 조건 외 국가종합전자조달 등록 등 제품의 다른 필수 조건을 어떻게 다룰지 정해야 한다. 기본값을 임의 충족으로 채우지 않는다. 검수 조건 묶음 상태와 실제 종합 판정을 각각 보고하는 것이 우선이다.
5. **Q-009와 v03의 관계를 기록한다.** v03은 해당 공고 데모의 검수 기대값을 새로 제시했으므로 구 v02 공통 보류 기대를 그대로 정답으로 쓰면 안 된다. 다만 1224→1227 정정 확인과 업종군 사이 결합 관계의 해석은 별개다. 이전 공고문/화면 충돌 근거를 지우지 않는다. v03을 특정 차수의 평가 규칙으로 사용할 경우 출처·범위·검수 버전을 기록한다. 발주기관의 공식 해석을 확인했다고 승격하거나 모든 공고에 같은 AND 규칙을 적용하지 않는다.
6. **날짜의 의미를 고정한다.** `03_판정검토32`는 기준일 2026-08-18을 사용한다. 기존 원문 검수에는 방문 지정일 8/20~21이 기록되어 있다. 그 기준일이 실적/판정 산정일인지 데모의 현재시각인지 분리해야 한다. 확인서 제출=예를 쓰려면 합성 시나리오의 사건 시점도 설명 가능해야 한다. '예정일 경과'를 실제 미이행으로 추론하지 않는다.
7. **기대값은 실행 입력과 독립적으로 둔다.** J13 ID를 보고 합격을 반환하거나 Excel expected를 저장 판정으로 직접 입력하는 방법은 검증이 아니다. 조건·예외를 실행하는 제품 엔진이 상태와 사유를 내야 한다.

고정 EvidenceBundle로 Copilot만 평가하는 검사와 실제 원문→추출→엔진→화면 검사를 나눈다. 전자는 오류 위치를 분리하고, 후자는 수동 fixture로 우회되지 않은 제품 연결을 증명한다. 두 검사를 서로 대신하지 않는다.

J13/J14는 변경 원인·반전 방향의 설명을, J15는 '등록이 없어도 왜 충족인가'라는 예외 후속을, J16은 왜 아직 확정할 수 없는지와 추가 답변/가정/실행을 포함하는 3~4턴 업무로 검사한다. 추천 문장을 외운 답이 아니라 같은 목적의 새 표현도 사용한다. 수용할 출력은 필수 사실과 상태·행동 기준으로 정하고 문장 완전 일치를 강요하지 않는다.

남원만으로 제출서류 여러 단계/날짜 혼합을 충분히 검사할 수 없으므로 J05 구내식당의 14시 전자입찰 vs 15시 방문접수, 필수 vs 협조, 선정 후 vs 계약 시 제출을 회귀에 남긴다. 우치공원은 요건 삭제·미적용, 한림대는 metadata 변경과 실제 조건 유지라는 다른 실패 축을 확인한다. 남원의 코드 변경 규칙을 다른 공고의 기본 가정으로 만들지 않는다.

## Q-019 — 데모 기대값의 적용 범위와 완료 계약

**근거:** Excel의 네 조건 묶음과 제품 종합 판정의 필수 조건 집합이 같다고 확인되지 않았다. v03의 기대 반전과 기존 Q-009 보류는 서로 다른 검수 기준을 사용한다. 기존 적재 코드는 시나리오 답변을 가져오지 않는다. 최초 Job 미완료가 사라진 실행도 확인됐다.

**대안 A:** 회사 기본값을 충족으로 채우고 보류를 전역 해제해 네 기대값을 맞춘다. 입력과 원문 해석을 섞으므로 비권장.

**대안 B — 권장:** v03 입력·차수·검수 규칙·판정 범위를 명시한 독립 로컬 평가 묶음을 만든다. 검수 조건 묶음 결과와 제품 종합 판정을 각각 대조한다. 전체 참가 가능 데모가 필요하면 빠진 필수 조건도 명시적으로 검수하여 입력 명세에 반영한다. 회사값으로 해석 승인을 대신하지 않는다. 같은 Job 계약에 LangChain RAG·엔진 결과·후속 대화를 연결한다.

**대안 C:** 모든 법적 해석과 전체 서비스 기능이 확정될 때까지 분석/구현을 모두 중단한다. 독립적으로 가능한 입력·연결·조건별 회귀까지 막으므로 비권장. 공식 해석 대기는 해당 결론의 범위로 제한한다.

**결정할 사항:** (1) v03의 충족 범위 (2) 해당 차수의 업종군/예외 해석 적용 기준 (3) 확인서·법적 허가 합성 입력의 실제 필드 매핑 및 시간 기준. 결정 전에도 계약 설계와 조회/모델 없는 회귀 작업은 가능하지만 그 결정을 임의로 채워 엔진 합격을 보고하지 않는다.

## 이후 공용 DB에 맞출 입력 묶음

회사별 입력 JSON/표, 프로필과 공고별 답변의 매핑, 예/아니오/미확인 구분, 공고번호·차수·원문 hash·검수 규칙·기준일, 기대/실제 결과·사유·로그를 묶는다. 기존 대상과의 사전 비교 및 적용 후 확인 절차도 포함한다. 로컬 UUID·사용자 비밀번호·회사 실정보·비공개 원문 사본을 그대로 배포 자료에 싣지 않는다. 새 네 프로필과 기존 사용자 테스트 프로필은 별도로 유지한다.

이 산출물 작성과 공용 DB 실행은 별개다. 현재 승인 범위는 분석 및 이후의 전용 로컬 검증이며 공용 DB 쓰기는 수행하지 않는다.

## 목표 수준을 주장할 때의 한계

Notion의 64개 능력별 시나리오, 40/24 개발/보류 분리, 보류 반복, 3명×6과업, 완료율/근거충실도/지연 목표는 설계 제안이다. 작성·실행된 숫자로 바꾸어 보고하지 않는다. 남원 8개 판정 산출물로 이를 대신하지 않는다. 실제 준비된 시나리오와 실행 횟수/비용을 따로 기록해야 한다.

기본 응답 p50 8초·p95 20초는 원래 초기 검토 목표이고 전체 조건/비교는 별도 집계하도록 되어 있다. 현재의 복합 3회 시간으로 기본 응답 p95를 산출할 수 없다. 반복 실측 후 지연·완료율을 함께 비교한다. LangChain 연결, 인덱스 READY, 컨텍스트 감소 또는 스트리밍 각각을 속도 합격으로 간주하지 않는다.

따라서 도달 가능한 첫 결과는 '선택된 공고에서 근거를 찾아 회사 영향과 다음 행동을 이어서 설명하는 검증된 Job'이다. 전역 공고 검색·모든 회사 사실의 실제 인증·임의 지원 업무 실행·영속 대화까지 완성됐다는 뜻은 아니다. 이 경계를 공개하면서 원래 설계의 목표는 남겨 두는 것이 적절하다.
