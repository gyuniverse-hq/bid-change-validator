## Q-007 보완: 장문과 실제 원본 추출

- 전체 읽기 요청의 각 원문 부분에 위치·출처·처리 상태를 기록한다. 같은 내용의 중복 첨부만 정확한 문자열 일치로 한 번 검토하며 모든 원래 위치를 alias로 남긴다.
- 부분별 생성과 독립 의미 검증을 수행하고, 거절된 부분만 한 차례 보완한다. 미처리/검증 실패가 하나라도 있으면 PARTIAL을 유지하며 해당 원문을 표시한다. 키워드 8개 출현만으로 완료시키지 않는다.
- 문서 경로는 최대 10개 최초 batch와 3개 보완 batch, 동시 3개, 문서 모델 호출 최대 26회, 전체 150초로 제한한다. 일반 단일 답변의 기존 한도는 유지한다. 한도를 넘는 더 큰 문서는 여전히 PARTIAL일 수 있다.
- 긴 검증 이유로 모델 출력이 잘리는 실제 실패를 확인하여 이유 길이를 제한했다. 제목의 분류와 공고 전체의 조건 부재를 구분하고, 의무 주체·단서·약정과 업종군 관계의 불확실성을 보존하도록 했다.
- 새 ledger는 전체 문서 읽기 단독 과업 경로에 연결했다. 장문 읽기와 다른 도구를 섞는 모든 복합 자유 질문의 성공은 검증하지 않았다.

HWP 추출은 본문 제어문자를 일반 UTF-16 문자처럼 읽어 생긴 손상이다. [한컴 HWP 5.0 형식 문서](https://cdn.hancom.com/link/docs/%ED%95%9C%EA%B8%80%EB%AC%B8%EC%84%9C%ED%8C%8C%EC%9D%BC%ED%98%95%EC%8B%9D_5.0_revision1.3.pdf)의 제어문자 구조에 맞춰 본문 decoder를 수정했다. 정상 한자·Unicode는 보존하고 잘린/잘못된 제어문자는 실패로 처리한다. 추출기 식별자는 `HWP5_BODYTEXT_V2`다.

승인된 snapshot의 공개 문서 URL에서 v1/v2 HWP 원본을 확보했고, 원본 byte hash가 저장된 file hash와 각각 일치했다. 새 추출기로 HWP 및 동일 표준문서 4개 row를 **별도 로컬 snapshot**에 재추출했다. 기존 snapshot은 변경하지 않았다. 원본의 사람 시각 검수나 법적 해석 검수까지 완료한 것은 아니다.

| 자료 | SHA-256 |

| 기존 snapshot | `685064ae2b19a1e86232ce57bd3762ff3fb563c2568f41ac3bc2db4ee794443d` |
| 재추출 snapshot | `52cb91a7da8661949ecb38b5903337274febbf88b3f20b4d76ba12f7118102f0` |
| v1 HWP 원본 | `4867ca864d1af36ebeade7975599e268ff302b08c0527324781e109d768d192b` |
| v2 HWP 원본 | `50882dab8d29e5a2e0dccee99fb526b87611aa50247d9aed9e145b121202a087` |

재추출 후 v1/v2 모두 source readiness AVAILABLE, 각각 74 records다. 이것은 텍스트 준비도이며 분석·법적 판정 완료를 뜻하지 않는다. `scripts/reextract_copilot_snapshot.py`로 재현한 출력도 같은 hash였다. 이 CLI는 DB/네트워크에 연결하지 않고 원본 hash와 새 출력 경로를 검사한다. 공용 DB의 기존 손상 추출물은 그대로 있으므로 코드 반영만으로 그 데이터까지 수정되지는 않는다.

## Q-008 보완: 개별 조건과 실제 입력 경로

업종명+코드 표현을 회사 코드와 비교할 수 있게 정규화하고, 값과 원문의 코드가 모순되면 UNKNOWN으로 둔다. 원문의 확인된 문형만 다음 계약으로 연결한다. 다른 복합 문형의 기존 방어를 전역 해제하지 않았다.

- 수집·운반업 등록 보유, 또는 처분/재활용업 허가·직접 운반의 법적 허가 조건·필요 장비 조건의 개별 확인.
- 한 업종군 안에 명시된 처분/재활용업 대안.
- 현장 방문과 확인서 제출의 개별 확인.

명시적 재판정 POST에서 출처 hash·원문 위치를 가진 **새 분석 revision**을 추가한다. GET 조회나 기존 분석을 덮어쓰지 않는다. 동일 부모/출처 revision은 재사용하고, 문서 간 조건 충돌·여러 운반 요건의 모호한 대체는 중단한다. 규칙 버전은 `qualification-rules-v0.4`다. 현재 차수의 원문 보완을 건너뛴 변경 재검증도 차단한다.

확인 질문 API와 UI에서 필요한 허가·장비를 각각 입력한다. 기본값은 미확인이며, 원문 hash·정확한 필드·boolean 값·종합 답변의 일치를 서버에서 검사한다. 트럭 보유 문장이나 단순 yes/no만으로 제안/저장할 수 없다. 명시 확인 전에는 저장하지 않으며 재전송으로 판정을 중복 생성하지 않는다. 사용자 진술을 증빙 검증 완료나 회사 원장 수정으로 취급하지 않는다.

## Q-009 — 서로 다른 업종군 사이의 AND/OR 미확정

**근거:** 남원 참가자격에는 “아래 업종 중 해당 자격”이라는 상위 문구와 1) 처분/재활용업군, 2) 수집·운반업군, 운반 등록의 예외가 있다. 장문 모델은 1)과 2) 사이를 OR로 확장한 설명을 의미 검증에서 통과시켰다. 반면 최초 보완 판정은 두 요건을 각각 필수로 합산했다. J13~J16은 모두 1257을 가져 이 해석 차이를 판별하지 못한다. 자동 의미 검증 PASS가 독립 정답 보증은 아니라는 실제 사례다.

**대안 A:** 기존처럼 업종군을 AND로 합산한다. 원문 의도를 확인하지 못한 상태에서 참가 불가를 확정할 수 있어 비권장.

**대안 B:** 상위 “중”만으로 업종군을 OR로 합산한다. 운반 등록과 예외를 별도로 적은 이유를 누락할 수 있어 비권장.

**대안 C / 권장:** 번호별 개별 조건은 보존하되 군 사이 관계는 검수 전 UNRESOLVED로 둔다. 발주기관 원문 의도를 확인하거나 설계 대화에서 근거를 검수한 뒤 관계를 확정한다. 1227만 보유, 처분업만 보유, 양쪽 보유, 둘 다 미보유 프로필을 추가로 검수하여 AND/OR 차이를 평가한다.

**이번 구현:** C의 방어를 적용했다. 개별 SATISFIED/UNSATISFIED는 유지하지만 미확정 업종군을 임의의 전체 참가 결론으로 합산하지 않는다. 별도 확정 미달 요건이 없다면 insufficient_data를 유지한다. 새 분석은 PARTIAL 및 `SOURCE_GROUP_RELATION_UNRESOLVED` 진단을 가진다. 다른 지역/등록의 독립적인 미달은 그대로 참가 불가 근거가 될 수 있다. 모델 지침에도 번호 사이의 미확정 관계를 명시하도록 반영했다.

**설계 대화 전달 요청:** 남원의 1)과 2) 관계를 어떤 원문 근거로 확정할지 검토해 달라. 이번 개별 예외 연결 성공을 전체 자격조건 해석 완료로 바꾸지 말아 달라.

최종 Q-007 미완료 부분은 `u6`이다. 생성 모델은 총액·산출내역서·제출기한·취소 제한을 참가자격 외 제출 절차로 제외했고, 검증 모델은 이를 입찰 전 필수 조건 누락으로 판단했다. 업종군 미확정 설명은 최종 답변에 반영됐지만, 이 범위 불일치 때문에 전체 응답은 PARTIAL이다. 최종 답변에 어색한 말미와 내부 부분 ID 표현도 있어 표시 품질의 추가 보완이 필요하다. 중간 PASS 1회를 최종 완료나 반복 안정성 증거로 사용하지 않는다.

1. Q-007에서 참가자격 설명과 입찰서 제출 절차의 완료 범위를 같은 계약으로 정의하고, 생성·검증에 함께 적용한다. 화면에 보여줄 문장 품질까지 검사한다. 원문/검증 기준을 삭제하거나 PASS를 강제하지 않는다.
2. Q-009 업종군 관계와 평가용 합성 보충값을 원문 기준으로 검수한다. 확인 전에는 현재 보류 동작을 유지한다.
3. 전용 로컬 평가 DB에 재추출 자료·검수된 프로필·고정 계정을 준비한다. 자동 검사 계정은 유지되는 사용자 평가 환경이 아니다. 공용 DB 기존 자료 재추출은 별도의 승인된 작업이다.
4. 17번 표에 따라 실제 사용자의 자유 질문·이해도 평가를 실시한다. 장문 한 시나리오의 모델 검증을 자유 질문 전반의 신뢰도/성공률로 확대하지 않는다.
5. 평가 결과와 최신 develop 변화 확인 후 통합 여부를 판단한다. 이번 보완에서 merge·배포는 하지 않는다.
