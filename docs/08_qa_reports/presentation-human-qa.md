# 발표 데모 1건·Golden 3건 Human Click QA

> 상태: Proposed — **실행 결과 기록 전**
> 기준 코드: 2026-09-15 `develop` HEAD `2d51c1a`; 이후 코드가 바뀌면 다시 기록한다.
> 목적: 발표 중 클릭할 핵심 경로에 P0 오류가 없는지 직접 확인한다. CI green이나 저장된 판정이 있다는 사실만으로 통과 처리하지 않는다.

## 대상 확정

| 슬롯 | 공고/Case | 검증 목적 | 확정 상태 |
| --- | --- | --- | --- |
| 발표 데모 1 | 남원글로컬 `R26BK01684863` 후보 | 공고→회사 판정→근거→변경 비교의 기본 흐름 | 통합 담당자 최종 확정 필요 |
| Golden 1 | 공고번호·차수·Case ID 기록 | 정상 자격요건/근거 | 미확정 |
| Golden 2 | 공고번호·차수·Case ID 기록 | 불완전 추출·UNKNOWN/미달 경로 | 미확정 |
| Golden 3 | 공고번호·차수·Case ID 기록 | 변경/취소 또는 원본 경로 | 미확정 |

최종 3건을 임의로 정하지 않는다. 후보인 구내식당(`R26BK01633750`)과 남원글로컬은 **동일 입력의 추출 결과 변동**이 보고됐고, 한림대(`R26BK01687120`)는 첨부 일부만 읽힌 상태다. 우치공원(`R26BK01634263`)은 최종 차수 005가 **취소공고·첨부 0건 정상 상태**이므로 일반 자격판정 대신 취소 상태 표시/차수 확인 시나리오로만 사용한다. Golden Set v1.0 freeze manifest의 공고번호·차수·Version ID·Document ID·해시를 기준으로 입력 대상을 확정한다.

## 실행 전 고정할 것

- 테스트 환경(Oracle 또는 로컬), 코드 commit, DB revision, 사용 계정의 **회사 식별자**, 공고 차수, Case ID, analysis/judgment run ID를 기록한다. ID/PW나 쿠키는 문서에 남기지 않는다.
- Golden 계정은 각 회사에 연결된 테스트 계정을 사용한다. 다른 회사 계정으로 Case를 열어 403이 나오는 권한 격리 확인도 별도 테스트 Case에서 수행한다.
- 기존 저장 판정 조회는 읽기 경로다. `다시 검토`, Ask-back 제출, 제안서 업로드, 재검증은 새 run/데이터를 만들 수 있으므로 **별도 QA Case에서만** 수행한다. 발표용 저장 결과를 덮거나 동일 공고 Case를 중복 생성하지 않는다.
- 반복 추출 변동이 해결·검증되기 전에는 발표 데모 화면에서 재분석 버튼을 누르지 않는다. 결과를 안정화했다고 주장하려면 고정된 원문/청크로 반복 실행한 근거가 필요하다.

| 8 | 별도 QA Case에서 UNKNOWN→Ask-back→재판정, 변경 차수 재검증 | 제출 내용·새 판정·변경 근거가 일관되고, 같은 차수 `baseline=current` 재검증은 차단 | 상태 불일치/중복 실행: P0 |

### 발표 1건에서 추가 확인

- 미리 저장된 공고·Case·판정·근거를 사용해 **예상 화면과 실제 화면**을 사전에 대조한다. 남원글로컬의 변경 전후가 같은 회사에서 둘 다 미달일 수 있으므로, “변경 때문에 참가 불가가 됐다”는 서술을 결과 확인 없이 사용하지 않는다.
- 모든 화면의 진입/데이터 로딩 시간을 기록한다. `회사 기준으로 판정 가능한 공고`, 참가자격 검토 데이터, 새 분석은 서로 다른 API/계산 경로라 느린 원인을 한 가지로 단정하지 않는다. 사용자가 기다리는 동안에는 진행·오류·재시도 안내가 보여야 한다.
- `/guide` 마지막 `공고 찾기로 가기` 등 발표 중 눌러볼 이동 버튼도 확인한다. 버튼 하나라도 실패하면 해당 경로를 P0로 기록한다.

### Golden 3건의 차별화 확인

- 각 사례의 기대값은 **freeze manifest와 팀 검토표**를 대조해 정한다. 실제 결과를 기대값으로 덮어쓰지 않는다.
- 정상·PARTIAL/UNKNOWN·취소/변경 사례를 구분하고, “첨부 0건”이 곧 “수집 실패”라는 식의 추측을 하지 않는다. 우치공원 005의 첨부 0건은 취소공고의 정상 상태다.
- 반복 분석을 해야 하는 경우에는 동일 document ID·원문 해시·target chunk IDs·모델/설정·analysis run ID를 기록한다. 결과가 변동하면 화면 기능 성공과 추출 품질 실패를 분리해 보고한다.

## 기록 양식과 통과 기준

| 필드 | 기록할 값 |
| --- | --- |
| 환경/코드 | Oracle 또는 로컬, commit, 실행 시각 |
| 데이터 | 공고번호, 차수, Version ID, Document ID/해시, 회사 ID, Case ID |
| 실행 | 화면 경로, 클릭 동작, analysis/judgment/revalidation run ID, 응답 상태, 소요 시간 |
| 결과 | PASS/FAIL/BLOCKED, 기대값 대비 실제값, 스크린샷/근거 링크, 재현 횟수, 담당자 |

통과 조건: **발표 1건과 확정 Golden 3건의 공통 경로에서 P0 0건**, 권한 격리/원본 연결/직접 URL 진입 확인, 변경·취소 상태가 실제 차수와 일치. 미실행이나 외부 API/LLM 불안정으로 재현하지 못한 항목은 `BLOCKED`로 두고 PASS로 세지 않는다. 발표 직전 코드·서버·DB가 바뀌면 핵심 클릭 경로를 다시 확인한다.
