## 항목별 확인

### ① 청크 선별

기존 코드는 한 글자 한글 라벨도 top-level로 보고 자격 절 순회를 중단했다. 새 테스트의
`3. 입찰참가자격 -> 가./나./1)/다. -> 4. 입찰방법` 사례는 통과한다.

남은 반례:

- `3.1 입찰참가자격`은 rank 2, 그 아래 `가.`도 rank 2라 본문 시작에서 다시 중단한다.
- `1) 입찰참가자격`은 rank 3이라 `rank > 2` 조건에 의해 anchor가 되지 못한다.
- 회귀 테스트는 숫자 `3.` anchor 한 형태만 고정한다.

수치도 서로 충돌한다. 테스트 주석과 commit은 `39/59 -> 54/59`, 공유문은
`39/59 -> 56/59`다. 동일 입력·측정 코드·결과 artifact가 필요하다.

### ② clause safety 전처리

`「...법률」 제21조에 따른 업종코드 1253`과 주소 증빙 설명 괄호의 `또는`이 기존
정규식에 걸린다는 진단은 맞고 추가 테스트 5건이 해당 경계를 검증한다.

하지만 `_PARENTHETICAL_RE`는 괄호 의미를 구분하지 않고 전부 삭제한다. 다음 반례는
현재 코드에서 `unsafe_clause_reason(...) is None`이 된다.

```text
업종코드 1253 등록업체(공동수급은 허용하지 않음)
```

즉 실제 공동수급/부정 조건까지 검사 전에 사라진다. `잘못된 확정 0`은 해당 draft
fixture 안에서만 관측된 값이지 이 반례에 대한 안전 보장이 아니다. 법령 인용 제거는
유지할 수 있지만, 괄호는 삭제 대신 본문과 별도로 검사하거나 설명 괄호만 제한적으로
인식해야 한다.

### ③ 근거 검증 문장부호

생산 `_squash`는 공백만 제거한다. 아래 값은 같은 의미지만 직접 검증 결과
`RAW_NOT_FOUND_IN_SOURCE` 경로로 탈락한다.

```text
모델: 수집·운반업
원문: 수집․운반업
```

평가 하네스의 `normalize()`에는 NFKC와 점 문자 통일이 이미 있으나 생산 검증기에는
없다. 동일 정규화를 공유하되, 원문 보존 필드는 바꾸지 않고 비교용 문자열에만 적용해야 한다.

## 후속 수정 결과

검수에서 발견한 코드 반례 3종은 같은 브랜치에서 보완했다.

- 청크 위계를 `3.1 < 가. < 1) < 가) < (1)`처럼 단계별 rank로 분리하고,
  `3.1 입찰참가자격`과 `1) 입찰참가자격`도 anchor가 되도록 했다.
- 괄호 전체를 지우지 않는다. 주소 판정용 증빙서류 나열이라는 좁은 설명 괄호만
  제거하고, 공동수급·부정·대안 등 safety 패턴이 있는 괄호 내용은 검사 대상으로
  유지한다.
- 생산 근거 비교에 NFKC 및 가운데점 변형 정규화를 적용했다. 저장되는 `raw` 값은
  수정하지 않는다.
- 관련 파이프라인·canonical·quality-eval 회귀 테스트는 `85 passed`다.

최초 검수 시점에는 저장소 안에 fixture bundle과 실행 결과 artifact가 없어 전체
성능 수치를 재검증하지 못했다. 이후 사용자가 저장소 밖의 실제 경로를 제공해 아래와
같이 다시 실행했다. 코드 반례 해결과 20공고 성능 수치 검증은 구분해야 한다.
