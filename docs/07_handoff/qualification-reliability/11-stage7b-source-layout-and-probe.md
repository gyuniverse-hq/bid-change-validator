## 1. 이번에 재현한 문제와 근거의 한계

사용자가 공유한 화면 원문 내보내기 `붙여넣은 마크다운(1)(7).md`의 남원글로컬
참가자격 절을 읽었다. 대상은 R26BK01684863, 전북대학교 남원글로컬캠퍼스 본관동
생활폐기물 처리 용역이다. 원본 PDF나 현재 DB의 실제 블록 경계·차수와 대조한 것은 아니다.

검토한 형식:

- `1)「...`, `2)「...`: 번호 바로 뒤에 공백 없이 원문이 시작됨.
- `○ ...`: 독립된 업무 조건이 기호 목록으로 나열됨.
- `3` 다음 행에 `참가자격`: 절 번호와 제목이 줄바꿈으로 분리됨.
- `※ ...` 다음에 다시 `○ ...`: 각주 이후 별도의 요건이 이어짐.

이 브랜치의 기존 review plan-v1은 번호 뒤 공백을 요구하고 원형 기호를 조항 경계로
인식하지 않았다. 그 결과 서로 다른 업종 조건이 앞의 각주 후보에 묶이고, 지역·현장 확인
문장도 다른 각주 후보에 붙는 구조를 재현했다. 이 문제는 우리 새 경로의 후보 구성 결함이다.
과거 팀 로그의 모든 추출 변동 원인을 이것 하나로 확정하지 않는다.

### 화면 내보내기 발췌 재생 결과

참가자격 절의 번호/제목부터 마지막 해석 안내까지를 한 블록으로 입력했다.
Markdown의 `1\)`/`2\)`를 화면 표시 문자로 사용한 것 외에 조건 문구는 변경하지 않았다.
입력 SHA256: `591d5c01f1b080415e4911fd145308dd99f0db8dc5165a27b57b6dc7158eab7e`.

| 항목 | 이전 plan-v1 | 수정 plan-v2 |
|---|---|---|
| 검토 단위 | 5 | 13 |
| 업종 선택 조건과 운반업 조건 | 같은 NOTE 후보 안에 묶임 | 각각 CLAUSE로 분리 |
| 지역·현장 확인서 문장 | NOTE 후보 뒤에 묶임 | 각각 CLAUSE로 분리 |
| 실제 입력 문자열 재조립 | 일치 | 일치 |
| 모든 offset의 원문 slice | 일치 | 일치 |

13은 자격요건 13건이라는 뜻이 아니다. 제목·설명·각주도 포함한 검토 단위 수다.
LLM 호출 0회이며 이 수치를 요건 재현율/정확도 향상으로 사용하지 않는다.
원문을 한 블록으로 입력한 재현이므로 실제 DB의 분할 결과까지 동일하다고 단정하지 않는다.
공개 저장소 테스트에는 실제 내보내기 원문 대신 형식이 유사한 합성 문장을 사용했다.

## 2. 구현

### 조항 계획 v2

`review_plan.py`에 명시적인 밀착 번호·원형 기호·알려진 번호/제목 형식을 추가했다.
숫자/금액/기간/날짜와 알 수 없는 두 행을 임의의 제목으로 추정하지 않는다.
번호 없는 문장의 줄바꿈은 문맥 단절로 간주하지 않는다.
상위 조항 및 근처 각주는 문맥으로 제공하지만 법적 적용 관계로 자동 확정하지 않는다.
분리된 제목이 서로 다른 원문 블록에 있는 경우까지 이번 수정이 모두 복원하는 것은 아니다.

API의 `review_v1`은 실행 전략명, `qualification-review-plan-v2`는 내부 분리 규칙 버전이다.
새 API 모드를 추가하거나 기본 제품 경로를 자동 전환한 작업이 아니다.

### 기존 저장 결과 재생

plan-v1의 기존 `_heading`/`_ranges`를 그대로 유지했다. 저장된 그래프는 audit에 기록된
계획 버전으로 후보와 근거를 재구성한다. 알 수 없거나 빠진 버전을 최신 버전으로 대체하지 않는다.
저장된 계획과 원문 inventory 해시도 함께 확인한다.

변경 전 코드로 생성한 합성 plan-v1 snapshot을 gzip fixture로 고정했다.
이 fixture를 변경 후 코드가 그대로 읽는 회귀 검증을 추가했다.
기존 실행을 새 후보 ID로 덮어쓰거나 DB 내용을 마이그레이션하지 않는다.

### 다른 분리 규칙을 공고 변경으로 오인하지 않기

이전·현재 그래프의 계획 버전이 다르면 `CANDIDATE_PLAN_CHANGED`를 기록하고
비교를 REVIEW_REQUIRED로 둔다. 그 차이를 요건 추가/삭제/조건 변경으로 확정하지 않는다.
의미 변경을 확정하려면 두 차수를 같은 검증된 계획 기준으로 분석해 비교해야 한다.
과거 결과 자체는 보존하며 비교 작업이 자동으로 재분석하거나 저장하지 않는다.

## 3. 실제 제품 그래프를 반복 측정 대상으로 추가

기존 측정기의 `review_graph_v1`은 조항별 내부 의미 분석 경로였다.
이번에 추가한 `document_graph_v1`은 아래 제품 함수들을 사용한다.

```text
읽기 전용으로 고정한 공고/첨부/회사
→ 공고 그래프 추출 및 조항 간 관계 구성
→ JSON 저장 형식으로 직렬화/역직렬화
→ 저장 그래프 검증
→ 기존 회사 판정 연결
→ 같은 차수의 반복 분석 비교
→ 기준/현재 차수의 변경 비교
```

그래프는 메모리에서 JSON 왕복한다. 측정기가 운영 DB에 분석·판정을 저장하거나
HTTP 화면을 자동 실행한다는 뜻은 아니다. 실제 저장/API 테스트는 기존 CI에 별도로 있다.

- CLI 기본 비교: legacy, review_v1, document_graph_v1.
- Python measure 함수의 기존 기본값은 호환성을 위해 유지한다.
- 원본 문서 명세가 없으면 없는 문서를 EXTRACTED로 만들어 넣지 않는다.
- 한 차수밖에 없으면 기준 차수를 만들지 않는다.
- SAME_VERSION_REPEAT와 VERSION_CHANGE를 구분하고 비교 상태/건수/진단을 별도 기록한다.
- 공고일/제출마감일의 명시 기준을 캡처하며 현재 날짜로 대신하지 않는다.
- 파일명/원문/회사 상세/모델 응답은 보고서에 복사하지 않는다. 내부 ID는 보호된 환경에서 보관한다.
- READ ONLY 트랜잭션, 호출 예산, 명시적 --live-model 조건을 유지한다.
- 안정적 오답도 가능하므로 accuracy=null, quality_verdict=NOT_ESTABLISHED를 유지한다.

```powershell
python -m apps.api.app.scripts.check_qualification_repeatability `
  --case-id "<실제 검토 건 UUID>" `
  --notice-number R26BK01684863 `
  --reference-date "<검증 기준일 YYYY-MM-DD>" `
  --live-model --runs 3 --max-calls 60 `
  --strategies legacy review_v1 document_graph_v1 `
  --output "<보호된 폴더>/namwon-repeatability-v2.json"
```

이 명령은 DATABASE_URL과 OPENAI_API_KEY가 안전하게 구성된 승인된 실행 환경에서만 사용한다.
이번 assistant 환경에는 해당 접속·키가 없고, Supabase 목록에서도 나라장터 프로젝트 접근을
확인하지 못했다. 키를 채팅에 붙이거나 공개 저장소에 넣지 않는다. 실제 모델 실측은 실행하지 않았다.
