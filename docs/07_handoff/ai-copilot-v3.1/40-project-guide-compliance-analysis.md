## 요구사항의 구분

가이드의 프로젝트 내용에는 문서 기반 RAG, 벡터 저장·검색, LangChain을 활용한 벡터DB와 LLM 연결, one-shot/few-shot 프롬프트, 모델 선택, 테스트·개선이 명시되어 있다. 필수 GitHub 산출물은 수집 데이터·전처리 문서, 아키텍처, RAG 연동 코드, 테스트 계획·결과다.

청크 500~1000토큰, overlap 10~20%, k=4~5는 시작 예시이지 고정 합격값이 아니다. reranking/streaming/GraphRAG/LangGraph는 필수가 아니다. 가이드는 단순 RAG를 먼저 정상화하고 필요성과 측정에 따라 기능을 추가하도록 한다.

LangChain 프롬프트 사용만으로 과제 평가자가 인정하는 범위는 가이드에 더 구체적으로 정의되어 있지 않다. 따라서 '패키지가 있으니 충족'으로 보고하지 않고 현재 UI 요청에서 검색과 LLM 연결을 실제 실행·설명 가능한 상태로 만드는 것을 권장한다.

## 재사용할 코드와 변경 경계

FAISS 저장/검색, 추출기·청킹, 원문 위치 metadata, fingerprint/세대 관리, 회사 판정 엔진, 동의·권한·예산·명시 실행 승인·출처 검증은 재사용한다. LangChain 도입 때문에 회사 판정이나 저장 권한을 LLM으로 옮기지 않는다.

LangChain Retriever가 기존 차수별 FAISS 검색을 호출하고 Document와 metadata를 반환하도록 연결한다. 질문·검색 근거·예시를 LangChain 프롬프트/실행 파이프라인으로 결합하고, 예산·timeout·사용량 기록을 유지한 모델 adapter로 답변을 생성한다. 공식 모델 adapter를 채택할지는 현 OpenAI SDK 의존성과 호환성을 검사한 뒤 결정한다. 단순 문자열 렌더링 또는 사용되지 않는 import만 추가하는 것으로 끝내지 않는다.

공식 참고: https://docs.langchain.com/oss/python/deepagents/retrieval — 기존 지식 저장소 재사용, retrieve-then-generate, 선택적 검증을 포함한 구조를 설명한다. LangGraph 전면 전환은 이 요구의 전제가 아니다.

## 권장 두 경로

1. 준비 경로: 원문 확보 → 추출/정리 → 청크 및 원문 위치 저장 → 변경 청크 임베딩 → 차수별 인덱스 저장 → READY 확인. 요청 중 자동 전체 구축은 하지 않는다. 신규/변경 차수만 준비하며 unchanged 청크 재사용에는 텍스트 hash와 임베딩 모델/차원/청킹 버전을 포함한다.
2. 질문 경로: 현재 사용자·회사·공고 차수 확인 → LangChain 검색 → 관련 근거와 예외 확보 → 예시 포함 프롬프트 → LLM → 기존 검증 → 답변.

회사 현재 판정은 DB/규칙 결과로 읽고, 공고 설명만 문서 검색으로 보강한다. 공고 변경 비교는 000/001을 명시적으로 분리해 검색하고 연결된 결과를 비교한다. 다른 차수 혼입 방지를 제거하지 않는다.

전체 참여 준비는 k=4만 읽고 전체 완료라고 해서는 안 된다. 검토 범위를 자격/서류/일정/예외 등으로 나누고 각 범위의 근거와 미확인을 추적한다. 전수 검토가 필요하면 별도 작업으로 처리·재사용하되, 단어 '준비' 때문에 매 질문마다 전부 넣는 기본 동작은 줄인다. 이 부분은 Q-017의 원래 job 완료 기준 보존과 함께 설계해야 한다.

## Q-018 판단안

문제: 필수 기술이 구 Document QA 일부에만 있고, 현재 평가한 v3.1은 그 경로를 우회한다. 벡터 인덱스 누락과 전수 원문 분기가 있어 기존 RAG 완료 보고를 현재 과제 준수 증거로 사용할 수 없다.

대안 A: 구 경로의 ChatPromptTemplate를 근거로 준수 주장. 실제 데모 흐름과 어긋나므로 비권장.

대안 B(권장): 기존 저장소/보호장치에 LangChain 검색·프롬프트·모델 연결을 명확히 넣고, 사전 인덱싱과 질문 경로를 분리한다. 기존 자산 재사용으로 변경 범위를 제한한다.

대안 C: 전체를 LangGraph/새 VectorDB로 교체. 가이드 필수가 아니며 회귀 범위를 키우므로 현시점 비권장.
