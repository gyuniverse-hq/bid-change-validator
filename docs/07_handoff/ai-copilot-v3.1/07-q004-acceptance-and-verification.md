## Q-004 — 적용한 결정과 근거

사용자가 진행을 승인한 B 방향을 구현했다. 답변 생성 전에 서버가 요청별 필수 항목을 정하고, 생성·검증·수정·재검증에서 같은 기준을 사용한다.

| 변경 | 동작과 이유 |
|---|---|
| 완료 기준 고정 | `acceptance.py`가 확인 질문별 조건·수치·예외, 회사정보 요약의 소재/규모·인력·실적·업종/인증 항목을 고정한다. 검증기가 새로 만든 자유문장 누락 항목은 완료 조건을 추가하지 못한다. |
| 명시적 요청 범위 유지 | “판정에 사용한 회사정보만 요약해줘” 같은 좁은 요청은 READ_PROFILE로 유지한다. 복합 요청까지 이 규칙으로 축소하지 않는다. 일반 표현은 기존 planner로 간다. |
| 질문과 단정 분리 | `speech_act`와 검증기의 독립적인 `observed_act`를 비교한다. “6억 이상인지 확인”에는 조건 근거가 필요하지만 회사의 충족 증빙은 필요하지 않다. “이미 충족”이라는 주장을 질문으로 표시해도 거절한다. |
| 서버의 최종 완료 계산 | 고정 criterion ID가 빠지거나 중복·추가되면 PARTIAL. MET에는 근거가 존재하고 관련 SUPPORTED 주장 ID가 있어야 한다. 항목의 의미상 충족 여부 판단에는 여전히 모델을 사용한다. |
| 수정 경계 유지 | 통과한 문장을 수정으로 덮어쓰지 않는다. 실패/누락 항목에 허용된 ID만 채택하고 새 ID 충돌을 방지한다. 중복 수정 ID는 거절한다. |
| 진단 증거 보존 | 평가 runner가 생성 후보·수정 후보·판정·고정 기준 hash를 `model-traces.json`에 보존한다. 이번 자료는 합성 데이터이며 API 키를 포함하지 않는다. 사용자 응답이나 운영 로그에 후보를 추가한 것은 아니다. |

업종/인증의 빈 목록은 **정보 미등록**으로 설명하며 실제 미보유로 단정하지 않는다. 저장되지 않은 별도 면허 필드나 요청하지 않은 null 경력 연수를 필수 항목으로 만들지 않는다. 자료 자체가 없는 요청은 빈 근거 기준을 유지해 사과 문장만으로 PASS가 되지 않는다. 기존 45초·품질 호출 수·입출력 상한을 유지했다.

## 중간 실패와 수정 내역

- `q004-before.log`: 기준 helper를 만든 뒤 조정자에 연결하기 전 신규 검사 **2 failed / 7 passed**. 전체 수정 전 코드에서 모든 검사가 실패했다고 주장하지 않는다.
- `061023Z`: 격리 **3 failed / 347 passed**. 기존 합성 4턴 fixture가 빈 프로필을 FOUND로 표시했던 문제를 발견했다. 이를 UNAVAILABLE로 고치고 첫 턴 기대값을 PARTIAL로 강화했다. 나머지 세 턴은 PASS다. 이전 4턴 결과를 소급해서 고치지 않았다.
- `061429Z`: 실제 모델 pytest **FAIL**. API 상태만 보면 6회 PASS였으나 세 번째 요약에서 인원 값이 빠져 독립 값 검사가 실패했다. planner가 요약에 판정 작업을 추가한 것이 기준을 바꿨다. 명시적 프로필 전용 요청의 범위를 서버에서 유지하도록 수정했다.
- `061838Z`: 실제 모델 pytest **FAIL**, 대화 5회 PASS / 1회 PARTIAL. 별도 면허 필드를 요구한 기준과 수정 응답의 ID 처리 문제를 발견했다. 저장된 업종/인증 범위로 기준을 명확히 하고, 통과 문장은 고정한 채 허용된 수정 ID만 채택하도록 고쳤다.
- 이후 최종 소스에서 격리·실제 DB·모델 대조군·브라우저 검사를 실행해 위 표의 결과를 얻었다. 중간 실패와 최종 성공의 후보/판정 trace를 함께 보존했다.

## 환경·비용·재현

Python 3.12.14 / pytest 9.1.1, PostgreSQL 16.15. 테스트 전용 `bid-copilot-test-db`의 `127.0.0.1:57945/copilot_test`를 사용했다. runner가 컨테이너 식별자와 DB 이름·사용자·버전을 확인한 뒤 DATABASE_URL과 MIGRATION_DATABASE_URL을 함께 대체하고 dotenv 로딩을 막는다. `.env`, 기존 앱의 5432 DB, 공용 Supabase는 변경하지 않았다. 검사 계정/데이터는 fixture가 정리하며 테스트 DB는 재사용을 위해 유지한다. 검증용 웹/API 서버는 종료했다.
