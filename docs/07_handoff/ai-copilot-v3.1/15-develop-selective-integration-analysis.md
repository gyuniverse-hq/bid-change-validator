## 4. 직접 비교한 동작

동일한 검사 스크립트를 로컬·develop 소스 export·임시 결합본에 각각 실행했다. DB와 외부 네트워크를 막았고, 검증 모델은 제어된 stub이다. 실제 모델이 어떤 문장을 생성할 확률을 측정한 검사는 아니다.

| 재현 사례 | develop | 로컬 / 임시 결합본 | 해석 |
|---|---|---|---|
| 서로 다른 두 문장에 같은 claim ID 사용 | 두 문장 모두 SUPPORTED. 두 번째 문장이 첫 번째 ID의 verdict를 물려받음 | 둘 다 INSUFFICIENT, 검증 호출 0 | 로컬 차단을 가져와야 함 |
| 중복 ID가 있는 최종 envelope | 허용 | ValidationError로 거절 | 로컬 최종 계약 검사 유지 |
| 모델 불가 시 긴 원문 fallback | 13,150자, 2,500자씩 분할 | 150자와 명시적 생략/한계 안내, PARTIAL | 출력 제한 보완 필요. 생략된 원문의 접근과 과업 미완료 표시 유지 |
| `참가자격 전체` / 합성 원문 4개 조건 | 4개 모두 반환 | 1개만 반환, 소재지·인원·운반 조건 누락 | **로컬 검색 변경은 보완 전 통합 보류(Q-007)** |

중복 ID 사례의 두 번째 문장은 근거와 반대되는 내용이다. 모델에 실제로 검증 요청된 첫 번째 항목의 결과가 동일 ID의 다른 문장에도 할당되는 구조 문제를 재현한 것이다. 실서비스에서 이미 오답이 발생했다는 주장과 구분한다.

## 5. Q-007 — 전체 조건 요청에 대한 검색 범위 누락

**상태: OPEN / 로컬 원문 검색 변경을 그대로 가져오지 말 것.**

**근거**

- 로컬 `readiness.py::read_passages`는 broad 요청에서도 키워드 일치와 추정 제목 그룹으로 원문을 고른다.
- 같은 물리 section 안에 `1. 참가자격: 등록증`, `2. 소재지: 전북`, `3. 상근 인원`, `4. 직접 운반 허가·차량`을 둔 합성 입력에서 `참가자격 전체` 질문에 첫 항목만 반환했다. develop은 네 항목을 반환했다.
- 로컬 `ProductTools.documents`는 passage가 있으면 READ_DOCUMENT를 FOUND로 표시하고, 원문 자체가 AVAILABLE이면 검색 단계에서 빠진 세 항목을 자동 한계 문장에 추가하지 않는다. 따라서 후속 생성·완료 기준은 이미 누락된 근거를 모를 수 있다.
- 이번 실행은 **검색 누락까지 재현**했다. 실제 모델이 최종 PASS를 잘못 반환하는지는 실행하지 않았다.

**대안**

A. 전체 요청에서는 확인 가능한 전체 원문 범위를 유지하고, 입력 예산을 넘으면 누락 항목·범위를 명시해 PARTIAL로 처리한다. 세부 질문은 별도 검색 최적화를 사용한다.

B. 검수된 자격조건 섹션·필수 조건 목록을 만들고, 목록 전체가 검색·설명됐는지 확인한다. 범위와 누락을 검증할 수 있을 때만 전체 완료를 허용한다. 추가 설계·평가 자료가 필요하다.

**권장안**

단기에는 A. develop의 broad 읽기 원칙을 유지하고 로컬의 입력 예산·한계 고지를 결합한다. 제목 추정에 따른 검색 축소는 우선 point 질문 최적화로 제한한다. 기존 로컬 테스트 `test_large_physical_section_does_not_select_every_topic`와 새 누락 사례를 함께 검토하여 “전체 자격조건”과 “급식 실적만”의 범위를 분리해야 한다. 조건 누락을 정당화하도록 기대값만 바꾸지 않는다.

**설계 대화 전달용**

> Q-007: 로컬의 broad 원문 검색은 `참가자격 전체` 요청에서 소재지·상근 인원·직접 운반 조건을 누락하는 합성 사례가 재현됐습니다(4개 중 1개 반환). 이 누락이 모델 입력 전 발생하므로 생성 후 검증만으로 회복하기 어렵습니다. 전체 요청은 확인 가능한 원문 범위를 유지하고 예산 초과를 PARTIAL로 표시하는 A안을 우선 권장합니다. 섹션별 필수 조건 목록을 검수해 추적하는 B안은 후속 설계로 둡니다.
