- 이 범위에서 사용자 평가 직전까지 구현·필수 검증하는 것이 이어갈 목적이다. 새로운 자유질문 사례를 계속 추가하며 범위를 늘리지 않는다.

## 3. 구현 방향

질문 버튼이 기존 자유질문 계획기에 문장만 보내는 구조로 끝내지 않는다. 서버의 Job·질문 카탈로그로 `job_id`, `question_id`, 계약 버전, 필요한 자료, 조회 도구, 답변 범위·형식, 완료 기준, 노출 가능 상태를 고정한다. 모델은 실제 선택 공고·회사 자료로 답하고, 메뉴 밖 업무를 새 완료 조건으로 덧붙이지 않는다. Golden 기대 답변을 제품 응답에 넣지 않는다.

| 질문 | 답변 범위와 완료 기준 |
|---|---|
| 무엇이 바뀌었나요? | 기준·현재 차수와 원문 근거, 구조화 값 변경/원문 표현 차이 구분. 분석상 추가·삭제를 실제 법적 조항 변경으로 단정하지 않음 |
| 우리 회사에 어떤 영향이 있나요? | 개별 요건 영향과 종합 판정 분리. 동일 회사·규칙·기준일의 연결된 비교가 없으면 비교 불가 이유를 설명. 과거 참가 가능을 추정하지 않음 |
| 무엇을 확인해야 하나요? | 앞서 확인한 변경을 반복하지 않고 남은 확인사항·이유·행동을 정리. 앱에서 입력 가능한 것과 외부 확인을 구분 |
| 필요한 서류, 기한, 방법은? | 서류별 단계·기한·방법·제출처를 연결. 필수/조건부/참고·협조를 구분. 원문에 없는 값은 확인 필요로 표시 |
| 준비 순서는? | 이전 서류 정보를 재사용하여 선행조건과 일정 순서로 정리. 지난 기한은 과거 이행 확인 대상으로 표시. 실제 제출 완료로 간주하지 않음 |
| 아직 확인하지 못한 것은? | 같은 Job에서 해결하지 못한 내용만 제시. 자료 부족·검색/검증 실패·회사 확인 필요를 구분하고 이유와 다음 행동 안내. 없으면 해당 범위에서 없다고 설명 |

답변 기본 화면은 결론·핵심 근거·다음 행동 중심으로 짧게 한다. 상세 근거와 검토 상태는 접는다. 내부 F/C/K ID, 모델 검증 지시문을 사용자 본문에 노출하지 않는다. 설명 완료와 회사의 현실 자격·실제 제출 완료는 별개다. 적절한 한계 설명도 질문 완료가 될 수 있으며, 실제 증빙 확보를 설명의 완료 조건으로 요구하지 않는다.

회사·공고·차수 또는 근거가 바뀌면 이전 답변을 그대로 재사용하지 않는다. UI 노출 조건은 서버에서도 확인한다. 자료가 없으면 허위 정상 답변을 내지 말고 선행 작업을 안내한다. 최초 화면은 선택형을 기본으로 하며 자유질문 확장은 별도 후속 범위로 둔다.

3. 기존 검색·도구·검증을 재사용하여 카탈로그와 UI를 연결한다. 제한된 질문에서 자유질문 계획으로 범위가 다시 늘어나지 않게 한다.
4. 모델 없는 검사는 질문 ID·도구/데이터 경계·전후 비교 부재·출처·권한·읽기 비저장·완료 상태·UI 노출을 중심으로 변경 영향 범위만 실행한다. 문서 이동 때문에 DB·모델 검사를 다시 돌리지 않는다.
5. 실제 모델 검증은 같은 대화에서 세 질문을 순서대로 실행한다. 변경 대응은 남원과 우치공원/한림대의 차이 유형, 참여 준비는 구내식당의 단계·기한·미확인 정보를 확인한다. 기존 호출 하나의 API·화면·원문 결과를 함께 검토하고 중복 호출하지 않는다. 공고 간 전용 규칙을 정답으로 하드코딩하지 않는다.
6. 실패는 원인과 영향 질문을 기록하고 관련 범위만 재검사한다. 미실행·실패 질문은 노출 승인하지 않는다. 성공 문장만 골라 검증 완료로 포장하지 않는다.
7. 검증된 적용 범위만 UI에 제공하고 사용자 평가 창·계정·질문 순서를 안내한다. 준비됐다고 판단할 수 없으면 정확한 차단점을 보고한다. 최초 평가 범위를 넘어서는 자유질문 확장은 후속 작업이다.

진행 보고에는 **전체 순서 / 현재 작업 / 남은 작업**을 계속 표시한다. 큰 설계 문제가 생기면 증거·대안·권장안을 Q 형식으로 기록한다. main/develop 직접 수정, 기존 작업 삭제, 공용 DB 변경, merge·배포를 하지 않는다. commit/push는 이번 인계 요청에 포함하지 않는다.
